Offline Draft Sync

This is sample content. Every region of this document is a worked example built on the invented feature NIMBUS-101, and each one is waiting to be filled with a real flow.

What this flow is

The one paragraph to read before the drawing.

This is the replay path: what happens to a draft written while the device was offline, from the moment the connection returns to the moment it is either in the drafts table or handed back to a person. The change under review moves where the write acknowledgement is checked, so the second branch is the point it turns on — everything above that branch behaves as it did.

The replay path

Every step, every branch, and both ways the flow can end. Each node in the drawing opens that node's entry below it.

The same flow in words

Seven steps, read top to bottom. The flow starts at Connection returns (start) and goes to Drain the outbox (step), then to the first branch, Version unchanged? (decision). On yes it carries straight on to the second branch. On no it takes the failure branch out to Merge the draft (step), which rejoins the main path at that same second branch rather than ending on its own. The second branch, Write acknowledged? (decision), is the one this change turns on: on yes the flow ends at Drafts in sync (end, success), and on no it ends at Stop and report (end, failure). Those two terminals are the only ways out, and nothing loops back.

  1. Connection returns → Drain the outbox — ordinary next step.
  2. Drain the outbox → Version unchanged? — ordinary next step.
  3. Version unchanged? → Write acknowledged? — affirmative branch, labelled yes.
  4. Version unchanged? → Merge the draft — failure branch, labelled no.
  5. Merge the draft → Write acknowledged? — ordinary next step; this is the rejoin.
  6. Write acknowledged? → Drafts in sync — affirmative branch, labelled yes.
  7. Write acknowledged? → Stop and report — failure branch, labelled no.

What each step does

One entry per node, in flow order. Exactly one is open at a time, and opening one closes the rest.

Connection returns start

The device regains a usable connection and the sync worker wakes. Nothing is sent yet. It fails when the connection is reported up but no request completes, in which case the worker sleeps and the whole flow starts again from here.

Drain the outbox step

Reads every queued draft in the device sequence it was written in, so replay order matches write order. It fails when the outbox holds an entry whose draft has since been deleted locally, which is dropped with a log line rather than stopping the drain.

Version unchanged? decision

Compares the version the draft was written against with the version the server now holds. Yes means nobody edited it elsewhere; no means it diverged while the device was offline. It fails when the server cannot report a version at all, which is treated as no.

Merge the draft step

Keeps both copies and records which is which, rather than choosing between them. It fails when the two copies cannot be reconciled without losing text, in which case both are kept and the draft is marked for a person to read.

Write acknowledged? decision

The branch this change turns on. It waits for the drafts table to acknowledge the write before the outbox entry is cleared. It fails when the acknowledgement arrives after the wait ends, which the change makes a no rather than a silent yes.

Stop and report end · failure

The failure ending. The outbox entry is left in place so the next run retries it, and the reason is surfaced where a person will see it. Nothing is discarded here; a draft that reaches this ending is still on the device.

Drafts in sync end · success

The success ending. Every queued draft is in the drafts table, the outbox is empty, and the device and the server hold the same version. This is the only ending that clears the queue.
