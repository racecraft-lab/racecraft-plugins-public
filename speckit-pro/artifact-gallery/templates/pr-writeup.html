NIMBUS-101

Offline Draft Sync

Sample content. Every region of this write-up is a worked example built on the invented feature NIMBUS-101 Offline Draft Sync, and each one is replaced when the template is filled with a real feature.

Why this change was made

Every keystroke in the draft editor went straight to the server, so a connection that dropped mid-sentence lost whatever had been typed since the last write that landed. Authors on conference wifi worked around it by drafting somewhere else and pasting in, which is the point at which the editor stopped being the place the work happens. NIMBUS-101 puts a local queue in front of the network so the editor never blocks on it.

How it behaved, and how it behaves now

Before. Each keystroke was a write to the server, and a dropped connection lost everything typed since the last one that landed.

After. Each keystroke is a write to a local queue, and the queue replays in the order the edits were made once the connection returns.

What each changed file does

packages/editor/src/draft-queue.ts — new

The queue itself. Holds edits in the order they were made, replays them one at a time when the connection returns, and stops at the first clash rather than merging past it.

packages/editor/src/draft-queue.test.ts — new

Covers replay order, the stop-at-first-clash boundary, and a queue that survives the tab being closed and reopened on the same device.

config/editor.json — changed

Turns the queue on behind offline_drafts and sets how many edits it holds before it asks the author to reconnect.

What this change deliberately leaves out

  • Not background sync. Nothing is sent from a closed tab. The queue replays when the author comes back to the draft.
  • Not shared editing while offline. Two authors still cannot work on one draft with either of them disconnected.

How it was checked

  • Passed. Unit tests over replay order, the stop-at-first-clash boundary, and a queue reopened in a new tab — fourteen cases, all green.
  • Pending. The manual run that drops the connection mid-sentence and reconnects, which is booked for the staging soak on Thursday.

What happened while it was built

Only tasks that reported something appear here, in the order the record was written, and a task that was retried appears more than once.

  • T007. The queue was written against the editor's existing save call, which turned out to debounce. The debounce had to move behind the queue so the order of the edits stays the author's rather than the timer's.
  • T009. Clash detection needs the stored copy's version, which the read endpoint did not return. Added it there rather than fetching the draft a second time on every replay.
  • T007. Re-run after the debounce move. This run replayed against a real connection instead of a stub, and that is what surfaced the ordering defect the first run had hidden.
