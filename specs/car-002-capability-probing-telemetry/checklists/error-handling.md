## Probe Timeout, Retry & Budget Bounds

- [x] CHK006 Is a per-invocation probe timeout required (a bound on each live `claude` call) so a hanging probe cannot stall the run indefinitely? An "explicit timeout" appears only as a research-level `subprocess` implementation note, not as a spec/plan requirement or a bounded value. [Completeness, Spec §FR-003 — remediated: explicit per-invocation timeout required, value recorded in snapshot probe metadata]
- [x] CHK007 Is a retry policy for transient probe failures specified — whether a failed or timed-out invocation is retried at all, and if so how retries are bounded? No requirement mentions retries anywhere in the artifacts. [Completeness, Spec §FR-003 / Edge disposition (2) — remediated: NO automatic retries; transport-class failures abort for an operator rerun]
- [x] CHK008 Is the interaction between retries/timeouts and the ~20-invocation budget defined — whether the ceiling counts *matrix cardinality* (pre-flight only) or *actual live invocations*, so retries/re-probes cannot push the real live-call count past the bound at runtime "even when probes hang or error"? [Clarity, Spec §FR-003 — remediated: bound counts actual live invocations = precomputed matrix cardinality (no retries; overrun surfaced pre-flight)]
- [x] CHK009 Is the budget-overrun disposition defined — a matrix that would exceed the roughly 20-invocation bound is a matrix-definition error surfaced before any live call is made? [Completeness, Spec Edge "Budget overrun"; quickstart Part A]

## Record-Class Error Taxonomy (unavailable & misdelivery, non-scorable)

- [x] CHK013 Is the misdelivery class defined as the observed/delivered model ID not matching the binding's resolved qualified ID, and marked non-scorable for the requested route? [Completeness, Spec §FR-025; data-model Record 4 record-class rules]
- [x] CHK014 Is the boundary between a *misdelivery* (non-scorable) and a *documented resolver fallback* (which populates `fallback_index`/`fallback_reason`) specified when both surface as observed ≠ resolved — a precedence/disambiguation rule so a legitimate fallback is not misclassified as misdelivery? Fallback is always null under CAR-002's unset-proof probes, but the published contract is consumed by CAR-003+ where it can fire. [Clarity, Spec §FR-025 — remediated: precedence rule — non-null fallback fields ⇒ resolver fallback, misdelivery requires fallback-null difference (AC-2.3 separation)]
- [x] CHK015 Is the `record_class`↔`scorable` invariant (unavailable and misdelivery ⇒ `scorable:false`; success and null ⇒ `scorable:true`) required to be enforced by validation, rather than leaving `record_class` and `scorable` as independently-settable fields a fixture could contradict? [Measurability, Spec §FR-024 — remediated: class↔scorable invariant enforced by validation]
- [x] CHK016 Is deterministic validation required to check each record-class fixture satisfies its *semantic* class invariant (misdelivery ⇒ observed ≠ resolved; null ⇒ every nullable present-but-null; unavailable ⇒ cross-refs a snapshot observation), not merely structural schema conformance? FR-024's enumerated checks stop at schema validation + join + hash recomputation + sanitization re-scan + referential integrity. [Measurability, Spec §FR-024 — remediated: per-class semantic invariants validated beyond structural conformance]
- [x] CHK017 Is the mapping from `record_class` to `outcome.status` specified — which status (`completed`/`unavailable`/`error`) a misdelivery or an unavailable record must carry — so the two non-scorable classes are represented consistently in the replay outcome? [Clarity, Spec §FR-025 + data-model outcome — remediated: class→status mapping defined (unavailable ⇒ unavailable; success/null/misdelivery ⇒ completed; error reserved)]
