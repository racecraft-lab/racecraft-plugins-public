**Purpose**: Validate that the CAR-003 requirements governing real model and agent integration — named-agent dispatch through the installed plugin, effective-model observation, alias re-point attribution, effort-ladder probing, the pinned execution environment, authentication mode, cache-state isolation, and the scorer's own model surface — are complete, unambiguous, internally consistent, and objectively verifiable before implementation.

**Depth**: formal release gate. **Audience**: reviewer (PR). **Focus clusters**: proven dispatch versus asserted equivalence; observed effective model versus configured route; alias re-point attribution; environment and override contract; auth mode; cache isolation; the scorer as an LLM integration in its own right.

**Note**: This checklist is generated by the `/speckit-checklist` command based on feature context and requirements. It tests the requirements, not the implementation.

## Real Dispatch and Named-Agent Delivery

- [x] CHK001 - Is there a **requirement** — not only an acceptance scenario — that the plugin-namespaced `speckit-pro:<name>` spawn be proven from the transcript? US2 acceptance scenario 4 states the obligation, and FR-009 requires a "named agent" observation, but no requirement constrains the *form* of that name to the plugin-namespaced one or its *source* to the transcript. [Gap, Spec §FR-009, §US2 AS4]
- [x] CHK002 - Are the requirements explicit that named-agent delivery is read from run evidence rather than from the dispatch request that asked for it? [Clarity, Spec §FR-009, §FR-030]
- [x] CHK003 - Are requirements defined distinguishing "the requested agent was delivered" from "some agent was delivered", with the ambiguous and unidentifiable cases given a closed outcome? [Coverage, Spec §FR-031]
- [x] CHK004 - Is the mandatory-observation manifest required to enumerate every field the dispatch-fidelity claim rests on, rather than leaving the set open? [Completeness, Spec §FR-009]
- [x] CHK005 - Are the requirements consistent that a non-executable role emits no dispatch and no score bundle, so absence of dispatch evidence is never read as a dispatch failure? [Consistency, Spec §FR-012]

## Materialization-Versus-Dispatch Equivalence

- [x] CHK006 - Are the two branches of the FR-008 proof — executing installed-plugin agent policy versus proving content-hash identity over materialized destination bytes — established as **behaviorally equivalent**, or only asserted to be? The repository's own documented platform behavior is that plugin-shipped agents silently ignore `permissionMode`, `hooks`, and `mcpServers` while project- or user-scope agents honor them, so byte-identical content can still be interpreted differently by the loader. A content hash cannot detect this, because the bytes are identical and only the interpreter differs. [Gap, Spec §FR-006, §FR-008]
- [x] CHK007 - Do the requirements name which frontmatter keys are load-bearing for the treatment, so that a key the plugin loader ignores cannot silently enter the treatment claim? [Gap, Spec §FR-008, §FR-009]
- [x] CHK008 - Is the content-hash preimage stated precisely enough to distinguish content-hash identity from parsed-field equivalence, including that bytes are read back from disk? [Measurability, Spec §FR-008]
- [x] CHK009 - Are the requirements explicit that exactly one shipped materialization contract owns the rendered destination bytes, with no parsed-only or divergent evaluation materializer? [Consistency, Spec §FR-006]
- [x] CHK010 - Are requirements defined for the case where installed-plugin policy and canonical materialization differ in any byte, and does that case block scoring rather than degrade to the weaker proof? [Coverage, Spec §FR-008, §FR-030]
- [x] CHK011 - Is the destination path required to be verified separately rather than folded into the digest preimage, so an identical file at the wrong path is still caught? [Completeness, Spec §FR-008]

## Effort Ladder Probing and Admission

- [x] CHK024 - Is the full ordered effort set `low` through `max` required to be probed per role-eligible model, including `high` as the documented search origin the predecessor snapshot never observed? [Completeness, Spec §FR-040, §SC-018]
- [x] CHK025 - Is the admission strength of "configuration acceptance" bounded in the requirements? FR-002 admits effort support when the admitting surface accepts the configuration, which establishes that the client did not reject the value — not that the effort took effect. The spec applies an explicit bounded-claim discipline to attribution and to blinding but not to effort admission. [Gap, Spec §FR-002, §FR-040]
- [x] CHK026 - Are the requirements explicit that the print-mode canary probe is the sole admitting runtime authority and that every other surface may corroborate or invalidate but never admit? [Clarity, Spec §FR-002, §FR-004]
- [x] CHK027 - Is the closed effort ladder defined so that omitted, `inherit`, runtime-only, API-only, alias, aggregate, and topology-changing values can never become ordinary candidate efforts? [Coverage, Spec §FR-003, §FR-005]
- [x] CHK028 - Are requirements defined for disagreement between the admitting probe and a diagnostic observation, and does that disagreement force investigation or exclusion rather than a logged-and-ignored footnote? [Coverage, Spec §FR-004]

## Environment Contract and Override Proof

- [x] CHK029 - Is the execution environment **frozen and bound before execution** as a first-class pre-execution artifact? FR-009 requires parent controls to be *recorded*, and the assignment binds routes, hashes, and policies, but no requirement pins fast mode off, a permitted client-version range, or the parent-session model and effort for the run. A subagent that does not declare a model inherits the parent session's, so an unpinned parent silently changes the treatment. [Gap, Spec §FR-009, §FR-037, §FR-005]
- [x] CHK030 - Is "the complete environment-override proof" defined by an enumerated override surface? FR-039 requires that "every local override is proven unset" and the attribution record carries a single `override_proof_complete` boolean, but no requirement names which overrides constitute the complete set, leaving completeness unfalsifiable and the boolean a self-assertion. [Gap, Spec §FR-039]
- [x] CHK031 - Are the requirements consistent that fast mode is excluded as an ordinary candidate effort **and** governed as a run-time topology control, rather than only the former? [Consistency, Spec §FR-005]
- [x] CHK032 - Is a client-version change required to be a distinct refresh trigger, distinguishable from a platform re-point, at both the freeze and the run? [Consistency, Spec §FR-039, §FR-041]
- [x] CHK033 - Are the requirements explicit that no supported path may require setting the very override the proof requires to be unset, and is the resulting validation strategy stated rather than left implicit? [Clarity, Spec §FR-046]

## Authentication Mode

- [x] CHK034 - Is subscription authentication required to be sufficient on every supported path, with no supported path requiring an API key? [Completeness, Spec §FR-042]
- [x] CHK035 - Is the authentication mode required to be recorded for every run, and is the recording obligation traceable to a named mandatory-observation category rather than left as prose? [Measurability, Spec §FR-042, §FR-009]
- [x] CHK036 - Does recording the authentication mode also **constrain** it? The edge-case list names a run that executes under API-key authentication when only subscription authentication was expected, but the score-eligibility predicate has no authentication term and the closed failure-code taxonomy has no member for an unexpected auth mode — so a recorded-but-wrong auth mode has no closed outcome. [Gap, Spec §FR-030, §FR-034, §FR-042, §Edge Cases]
- [x] CHK037 - Are the requirements consistent that the catalog endpoint cannot be an admitting surface precisely because it yields evidence only under API-key authentication? [Consistency, Spec §FR-004, §FR-042]
- [x] CHK038 - Is the relaxation of the originating acceptance criterion required to be recorded as a dated amendment so later cross-artifact analysis does not read it as drift? [Traceability, Spec §FR-042]

## Cache-State Isolation Between Arms

- [x] CHK039 - Is cache-state isolation **evidenced per run**, or only precommitted as policy? US2 acceptance scenario 5 requires that one arm cannot warm another's cache and FR-049 requires a cache-state isolation policy to be bound before either arm runs, but no requirement obliges the run to record that the two arms actually used distinct cache roots. A bound policy is a precommitment, not evidence that it held. [Gap, Spec §FR-049, §US2 AS5]
- [x] CHK040 - Are cache-read and cache-write-by-TTL-class observations required to stay diagnostic and never become Pareto dimensions, given the closed shared token vector? [Consistency, Spec §FR-018, §FR-022]
- [x] CHK041 - Is the TTL-class key space closed and identical between the budget ceilings and the diagnostic measurement, so a ceiling can never be keyed differently from what it bounds? [Consistency, Spec §FR-022]
- [x] CHK042 - Are `cached_input_tokens` requirements consistent with the isolation rule, so that a cache-warmed arm cannot be compared against a cold arm as though the difference were a route property? [Coverage, Spec §FR-018, §FR-049]

## Scorer and Adjudicator Model Integration

- [x] CHK043 - Do the requirements apply any route-identity discipline to the scorer's and adjudicator's **own** model invocations? FR-047 makes family exclusion static in the frozen policy, and FR-035 binds scorer identity, calibration, and rubric — but nothing records the scorer run's observed model identity or subjects scorer routes to the re-point detection that candidate routes get, so a scorer alias re-pointing after the policy froze could move a scorer into a candidate's family with no recorded signal. [Gap, Spec §FR-035, §FR-047]
- [x] CHK044 - Is family exclusion required to be static and declared in the frozen policy so it carries no replay cost, and is the exclusion basis stated as a validity threat rather than a residual? [Clarity, Spec §FR-047]
- [x] CHK045 - Are requirements explicit that blinding is bounded rather than complete, with the residual measured and reported alongside any qualification claim? [Clarity, Spec §FR-048]
- [x] CHK046 - Is the pre-ballot leak check required to be mechanical and driven from the published freeze, and is artifact paraphrase or style normalization prohibited because it would add a non-frozen model call? [Consistency, Spec §FR-035, §FR-047]
- [x] CHK047 - Are the requirements consistent that the default suite makes zero live model calls, so no scoring or detection mechanism may introduce one? [Consistency, Spec §FR-022, §SC-019]
