# Data Integrity Requirements Quality Checklist: Artifact Brand Kit & Gallery Foundation

**Purpose**: Validate that the data-integrity requirements in `spec.md` and
`plan.md` (read together with `research.md`, `data-model.md`, `quickstart.md`,
and both `contracts/` files) are complete, unambiguous, internally consistent,
and objectively verifiable — before 21 catalog rows become the join key four
port specs and three workflow specs build on.
**Created**: 2026-07-28
**Feature**: [spec.md](../spec.md)

**Depth**: formal release gate. **Audience**: PR reviewer.

**Why this domain carries unusual weight here**: the catalog is the only
machine-readable interface ART-002…005 and ART-007/009/010 consume, and ART-001
ships **zero** artifacts. Every existence-conditioned check is therefore
vacuously true at merge time, so a defect in the *requirement* cannot be caught
by the *data* until a later spec trips it. Items about checks that cannot fire
in this feature are treated as blocking rather than advisory.

**Verification method**: the 21 seeded rows in `data-model.md` were re-parsed
and recounted programmatically against every count `spec.md` fixes, rather than
read. Runner behavior claimed by the contracts was read from
`speckit-pro/speckit_pro_runner/gates/payloads.py` and
`speckit-pro/speckit_pro_runner/helpers/read_only.py` directly, not inferred
from prose.

## Identifier Integrity — the Join Key

- [x] CHK006 - Is the identifier's **format** stated as a validated constraint rather than only as a description? FR-019 required identifiers "unique across the catalog and equal to the referenced file stem" and said nothing about their character set. Kebab-case appeared in Clarifications Session 2, `data-model.md`, and check B9, but no functional requirement mandated it — so the one property that makes the derived path well-formed rested entirely on a contract table. [Gap → Resolved] [Spec §FR-019 vs. contracts/gallery-validation-contract.md B9] **Resolved:** FR-019 now mandates filename-safe kebab-case — lowercase alphanumerics in hyphen-separated segments, no leading, trailing, or repeated hyphen, and no path separator, parent-directory segment, whitespace, or dot. B9 and both contracts restate it.
- [x] CHK007 - Given the path is **derived** from the identifier, do the requirements constrain the identifier tightly enough that the derivation cannot escape the gallery directory? FR-009 resolves `templates/<id>.html` by string composition from a field no requirement constrained to a filename-safe form. An id containing a path separator or a parent-directory segment composes a path outside `templates/`, and both the existence check (D1) and the orphan check (D3) would follow it. [Gap → Resolved] [Spec §FR-009, §FR-019] **Resolved:** FR-009 now states that because the path is composed rather than stored, FR-019's identifier format is what keeps resolution inside the gallery, and requires resolution to be rejected if it would leave the artifact directory. The format rule in FR-019 is the enforcing half.
- [x] CHK008 - Is the clause "identifiers ... equal to the referenced file stem" falsifiable under a derived path? It was not. The path is *defined* as `templates/<id>.html`, so its stem is the id by construction and the comparison can never fail. The clause was meaningful when a path was stored (pre-Session 2) and survived the change to a derived path unmodified, where it read as a check while asserting a tautology. [Gap → Resolved] [Spec §FR-019; Clarifications Session 2] **Resolved:** the clause is removed rather than reworded, and FR-019 states explicitly why — the comparison is true by construction, so validating the identifier's *form* is what the derived path actually needs. `data-model.md` and `contracts/routing-catalog-contract.md` carry the same reasoning so the deletion is not mistaken for an oversight.
- [x] CHK009 - Are identifier collisions specified as a failure with a named offender? **Pass** — FR-019 requires uniqueness, Story 2 scenario 5 states the duplicate case, and B9 names it. [Completeness] [Spec §FR-019; US2-AS5]
- [x] CHK010 - Is identifier **stability** across specs stated as a requirement, given that ART-007/009/010 will join on these values? The stability guarantee ("Entry `id` values are stable; ports never rename") lives only in `contracts/routing-catalog-contract.md`, which is a design artifact for this feature. No FR carries it, and no mechanism inside this feature could detect a later rename — a port that renames an id and its derived file together changes the join key silently. Enforcing it would need a baseline of the seeded ids for later specs to diff against, which is new machinery this feature has otherwise avoided. **Deferred to consensus** rather than resolved unilaterally: the trade is real, and the cheaper reading — that the contract's prose plus port-spec review suffices — is defensible. [Consistency] [contracts/routing-catalog-contract.md "Stability guarantees"]

[Gap → Resolved] [Spec §FR-019, §FR-020] **Resolved:** FR-019 now draws `source.origin` from the closed set `upstream` or `repository`, B10 rejects an unrecognized value at the shape layer, and both contracts plus `data-model.md` restate it as a closed two-member set.

[Gap → Resolved] [Spec §FR-015, §FR-017; contracts/gallery-validation-contract.md C1, C5, C6] **Resolved:** FR-017 now states the limit explicitly — "Count plus trigger-closure alone is not sufficient, and the limit MUST be stated rather than assumed" — and adds a third closure leg (see CHK022). - [x] CHK022 - Is FR-015's documentation obligation — that each signal carry "the named workflow evidence a routing consumer reads to decide it is present" — attached to any check? It was not. [Gap → Resolved] [Spec §FR-015, §FR-017] **Resolved:** new check C8 asserts set equality between `signals` and the signals documented in `SPA-CONTRACT.md`, and FR-015 now states the documentation obligation is itself validated. - [x] CHK039 - Is `schema_version` specified with a value, a type, and a position, so the assertion is unambiguous? **Pass** — Clarifications Session 2 fixes `"1.0"` as a string under a `snake_case` key, first in the document, and B2 asserts that exact value. Verified against the two precedents cited: both `tests/speckit-pro/suite-manifest.json` and `speckit-pro/speckit_pro_runner/install_inventory.json` carry `"schema_version": "1.0"` as a JSON **string**, so the stated precedent is accurate rather than approximate. [Clarity] [Spec §Clarifications Session 2; contracts/routing-catalog-contract.md]
- [x] CHK040 - Is the purpose of `schema_version` — a consumer reading an install cache that lags the repository — connected to any requirement about what a consumer should *do* on a version mismatch? The rationale for carrying the field is recorded, and B2 pins the value, but no requirement states the compatibility contract the field exists to serve. At `"1.0"` with one shape this is inert; it becomes load-bearing the moment a second version exists.   **Resolved by consensus (item 9) — state the failure posture, defer migration
  semantics.** Both analysts agreed on that split, and the second corrected the first on
  a point that mattered: **fail-closed is not direction-neutral.** The convention across
  Terraform, npm, and the Model Context Protocol is *reject newer, tolerate older*, and
  this catalog's stated concern is installed copies **lagging** the repository — so a
  flat reject-on-any-mismatch would break every existing install the first time the
  version is bumped. The posture is therefore stated directionally in
  `contracts/routing-catalog-contract.md`, migration is explicitly not specified, and
  enforcement is placed at the validate boundary because an agent reading the file as
  context does not branch on a version field. Two corrections came out of it: the
  field's original install-cache-lag justification is **unsound** (the catalog and its
  readers ship in the same version-scoped payload and cannot skew relative to each
  other) and is marked superseded rather than rewritten; and **no requirement validated
  the top-level shape at all** — FR-019 covered entries only. That is now FR-026.
