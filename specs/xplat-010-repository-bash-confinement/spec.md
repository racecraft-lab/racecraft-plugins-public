# Feature Specification: Repository Bash Confinement and CI Dispatch Guard

**Feature Branch**: `xplat-010-repository-bash-confinement`

**Created**: 2026-07-08

**Status**: Draft

**Input**: User description: "Confine repository-local Bash to GitHub CI/CD workflow dispatch glue only. XPLAT-009 removed Bash from the shipped plugin and its payloads, but the repository around it still runs on Bash: the test harness (~101 `.sh` files), top-level helper scripts, `.claude/hooks`, and one residual CI test-dispatch step. Port every active repo-local surface to Python 3.11+ standard library, prove zero check regressions per port, add a guard that fails any new Bash outside the workflow boundary, add container/runner preflight CI, make GitHub Releases readable by the public, and restore the deleted `estimate-spec-size` scoping estimator."

## Clarifications

### Session 2026-07-08 (Session 1 — suite manifest and count parity)

- Q: What is the per-layer/per-script field schema of `suite-manifest.json`, and what is the "expected-count source"? → A: JSON Schema 2020-12 contract. Top level `{schema_version, layers[]}`. Per layer: `{id, label, default (bool), execution ("execute"|"print-commands"), live_only (bool), integration (bool), counted_in_total (bool), dispatch ("python-module"|"internal-check"|"shell-legacy-transitional"), scripts[]}`. Per script: `{path (repo-relative), label, baseline (repo-relative pointer to the committed count-parity baseline file, or null)}`. The toolchain preflight is a layer with `counted_in_total: false`. The expected-count source is the **baseline pointer, not an inline integer** — the baseline file is the single count of record, eliminating manifest-vs-baseline drift. Composition changes are manifest-only edits; shipped-runner bytes change only when dispatch behavior changes.
- Q: What exactly must the dual-run diff in each port PR body contain? → A: A fixed block with six required items: (1) the exact bash capture command (`VERBOSE=true <script>`) and the port-run command; (2) the committed baseline path; (3) a unified diff of the ordered canonical check-name inventory, or the literal line "no differences — 1:1 preserved"; (4) the explicit count equality (`bash: N == python: N`); (5) an intentional-change statement (must be "none" for a clean port; any rename/drop flags the PR as a regression); (6) the count-ledger delta line appended to the running ledger.
- Q: At what granularity is "runtime count" measured for count parity (FR-010/FR-011/SC-003), and how must a ported unittest module's `{passed}/{total}` headline be computed? → A: Granularity is per individual assertion execution — every former `assert_*`/`_pass`/`_fail` call — not per former `set_test`; this covers both loop-generated repetitions and non-loop multi-assertion groupings within a single former `set_test`, not merely loop iterations. `{total}` MUST equal `(test methods not wrapped in a subTest loop/group) + (subTest units actually executed)`; bare `result.testsRun` MUST NOT stand in for `{total}` on any module with looping or grouped former assertions, since stdlib `subTest` execution never increments `testsRun` (only `addSubTest` fires per subTest). Ported modules MUST compute `{total}`/`{passed}` via a shared `unittest.TestResult` subclass overriding `addSubTest` (new shared utility under `tests/speckit-pro/lib/`). Five pre-existing modules print bare `result.testsRun` (`test-speckit-pro-read-only-helpers.py`, `test-speckit-pro-mutation-helpers.py`, `test-autopilot-phase-coverage.py`, `test-speckit-pro-runner.py`, `test-speckit-pro-gates.py`) and are exempt from retrofit: they were born pure-Python under XPLAT-005/006/007 (no bash predecessor) and are governed by the archived XPLAT-007 spec's FR-003, which required only pass/fail-meaning preservation, not numeric count parity — superseded precedent under an older contract, not a defect, and out of scope for a KISS/YAGNI-respecting rewrite. This exemption is retrospective and covers only those five: new ports and every other module MUST NOT copy the bare-`result.testsRun` pattern.
- Q: Does the shipped suite gate (`speckit-pro/speckit_pro_runner/gates/suite.py`) retire its native internal implementations of Layers 5/7/8 (`check_layer5`/`check_layer7`/`check_layer8`) when those layers are ported to manifest-named Python modules, or keep them behind a permanent equivalence test — and how is manifest/gate drift prevented? → A: Retire each native check at its own port-PR boundary (PR 5 for L5, PRs 7a/7b for L7, PR 8 for L8); no permanent equivalence shim is kept. The natives are not faithful baselines worth preserving: `check_layer5` is vacuously true (asserts on a `tools:` field none of the checked agents use), `check_layer7` validates an orphaned fixture directory no real Layer-7 runner reads, and `check_layer8` covers only 3 of the 6 files the real validator requires. Drift is prevented going forward by FR-007's fail-closed manifest-derived roster plus a deterministic drift-guard test asserting the gate's advertised roster and dispatch kinds match the manifest exactly; per-layer dispatch-kind assignment (`internal-check` vs. `python-module`) is deferred to the Plan phase.
- Q: What is the exact format of the committed count-parity baseline file (`tests/speckit-pro/parity/bash-to-python/<script>-baseline.txt`), and how are bash `set_test` names reconciled 1:1 with the Python port's check names? → A: Format is frozen: one line per executed `_pass`/`_fail` call in execution order (`NNN <canonical-name>`; grouped checks legitimately repeat the same name on consecutive lines — up to 11 observed), then a trailing `TOTAL: <N>` line where `N = PASS_COUNT + FAIL_COUNT`. Names are captured VERBATIM from runtime `VERBOSE=true` PASS/FAIL output (parsed only from lines matching `^\s*(.+?)\s\.\.\.\s(PASS|FAIL)$`), never reconstructed from source literals. A full census of all 14 active Layer-4 scripts and 7 Layer-1 validators found zero un-named `_pass`/`_fail` executions, so no positional `check-NNN` fallback naming is needed. Reconciliation with the Python port uses `unittest`'s `subTest` message parameter to reproduce each bash check name 1:1 (shipped precedent: `test-speckit-pro-read-only-helpers.py`, the XPLAT-005 port). Five normalization rules govern capture: (1) one line per outcome, names may repeat; (2) capture environment is pinned and recorded (non-root, matching CI); (3) one baseline file per (script, invocation-mode) pair for dual-mode scripts; (4) regeneration triggers include enumerated data files the script reads, not just script source; (5) never grep `assert_`-prefixed text for inventories — capture is always dynamic execution.

### Session 2026-07-08 (Session 2 — confinement guard semantics)

- Q: What exact `git ls-files` invocation does the confinement guard's enumeration use? → A: `["git", "ls-files", "-z"]` as an argv list (never a command string or `shell=True`), NUL-delimited, run from the repo root — matching the runner's existing argv-git idiom. No `--recurse-submodules` (the repo has none). Symlink targets are confined to the repo root via resolved-path checking before content reads, classified by the tracked link path's suffix. The `.github/workflows/` exclusion is a post-enumeration Python filter, not a pathspec. When git is unavailable or the tree is not a checkout, the guard fails closed with a missing-prerequisite diagnostic.
- Q: What is the allowlist entry contract for the 10 vendored `.specify/**` files, given the XPLAT-009 loader accepts only historical paths? → A: A new XPLAT-010 allowlist contract rhyming with the XPLAT-009 historical-allowlist schema: top-level `{schema_version, feature_id, entries[]}`; per entry `{path, categories[], reason, scope, release_readiness_excluded: true}` with `additionalProperties: false` and `release_readiness_excluded` required. The historical-path predicate is replaced by a `vendored_specify_helper` scope permitting only `.specify/scripts/bash/**` and `.specify/extensions/**/scripts/bash/**`. All 10 paths are pinned as individual per-file entries (no globs) so the set cannot broaden silently; any `.sh`/Bash-shebang file under `.specify/**` not on the list is a fail-closed blocking finding.
- Q: How does the guard compose into release readiness and CI? → A: A `repo_bash_confinement` check joins the release-readiness assembly mirroring the existing zero-bash composition (pass iff `blocking_count == 0`), with allowlisted entries surfaced under `release_readiness_excluded: true` so they are excluded from the positive evidence set (FR-004), and a live-scan guard case joins the default deterministic suite. Both ride existing required checks (`validate-plugins` sentinel; release-readiness leg) — no new CI job, no new required status check, zero branch-protection changes. The guard case performs a live repo-wide enumeration, never a fixed file list.
- Q: Which surfaces does the confinement guard's "active `bash`/`jq` invocation text" rule scan, and how are prose/self-reference false positives avoided? → A: Invocation-text detection runs only on executable and config-executed surfaces, never as a blanket text scan: Python files via AST inspection of `subprocess`/`os.system` call arguments (reusing the guard's existing `command_argv_contains_forbidden` / `shell_c_payload_has_forbidden_command` primitives against `PROHIBITED_COMMAND_NAMES`/`SHELL_RUNTIME_COMMAND_NAMES`), plus two structural JSON-value scans over the same primitives — `**/hooks.json` `command` fields and `**/package.json` `scripts` values (today: `docs-site/package.json`; hook `command` arrays are currently empty but the schema exists). No surface is text-scanned for prose mentions, because the rule is inherently about execution semantics — a bash/jq string has zero effect unless it sits in a syntax position that actually executes, so scoping to executable surfaces costs zero false negatives while avoiding the need to special-case 8+ legitimate `.sh`-path mentions in Markdown frontmatter and further prose references. `.claude/commands/*.md` frontmatter `scripts.sh:` path-references into FR-003-allowlisted vendored files need no new rule: the referencing document is governed by the referenced file's own allowlist status, not by scanning the document, and a reference to a future non-allowlisted `.sh` file is already caught by the suffix rule on that new file. `.git/hooks/**` and `.claude/settings.json` are untracked and therefore structurally invisible to any `git ls-files`-based guard — the same enumeration scope boundary recorded in this session's first clarification, not a gap specific to this rule.
- Q: Is the confinement guard's detection vocabulary bash-scoped (`.sh`/`.bash` + bash/POSIX-sh shebang only) or does it inherit XPLAT-009's broader `PROHIBITED_SCRIPT_SUFFIXES` (which would flag the 4 vendored `.ps1` files and force a 14-entry allowlist against FR-003's fixed 10)? Does `#!/bin/sh` count? → A: Bash-scoped only. The guard's detection vocabulary is `.sh`/`.bash` suffixes plus a Bash-family shebang (`bash` or POSIX `sh`, including bare `#!/bin/sh`); `.ps1`, `.bat`, `.cmd`, `.zsh`, and other non-bash-family suffixes or shebangs are outside its scope. This is logically forced by the already-ratified allowlist predicate (this session's prior entry): the `vendored_specify_helper` scope permits only `.specify/scripts/bash/**` and `.specify/extensions/**/scripts/bash/**` paths, which structurally cannot match the sibling `.../scripts/powershell/**` tree — inheriting XPLAT-009's broader shipped-payload vocabulary would flag the 4 vendored `.ps1` files as violations with no allowlist scope able to admit them, permanently contradicting FR-003's "exactly the 10." The 4 vendored `.specify/extensions/git/scripts/powershell/*.ps1` files therefore need no allowlist entry — they are never in the guard's detection set at all, not merely excluded from it. `#!/bin/sh` counts as in-scope (Bash-family, normalized alongside `bash`): today this is a no-op since all 10 vendored `.sh` files use `#!/usr/bin/env bash`, but ratifying it closes a future dodge at zero present cost. FR-001, FR-003, and SC-001 are updated accordingly. Flagged for Plan: FR-002's invocation vocabulary (`bash`/`jq`) should resolve to the literal `bash`/`jq` command-name pair, not XPLAT-009's superset that also includes `wsl`/`powershell`/`pwsh`, for the same bash-scoping reason — align at implementation time.

### Session 2026-07-08 (Session 3 — release-notes pipeline)

- Q: What is the machine-parseable grammar of the Release note block? → A: Exactly one fenced code block per PR whose info-string is `release-note` (the Kubernetes release-notes precedent the design concept named): multiline plain-English prose for consumers; limited inline markdown (emphasis, links, `-` bullets) allowed; raw HTML stripped by the composer; empty or whitespace-only counts as missing; zero or more-than-one block fails the check. Skip is expressed only by the `release-note/skip` label, never an in-block sentinel. A new `.github/pull_request_template.md` seeds the empty block under a `## Release note` heading. FR-021 and the Release Note Block entity are updated.
- Q: What does the composer put in Highlights for a PR with no block or with `release-note/skip`? → A: Skip-labeled PRs are omitted from Highlights (no consumer-visible effect by definition; they remain in the commit-list appendix). A feat/fix PR missing a block without the skip label (only reachable for commits merged before enforcement landed) degrades to its de-prefixed PR title so nothing consumer-relevant silently vanishes. When zero PRs in the range carry blocks, Highlights degrade to de-prefixed subjects and the appendix is always present. FR-023 updated.
- Q: Where does the composer run, with which token/endpoint, and how is it idempotent? → A: A new `release.yml` step in the post-publication branch gated on the release-created output; inputs are the release action's tag and body outputs plus the built-in workflow token (existing `contents: write` — no new secret, and never the elevated release token). Grounding correction discovered this session: release-please-action@v5 exposes no release-ID output, so the composer resolves the ID via `GET /repos/{owner}/{repo}/releases/tags/{tag}` and then `PATCH`es `/releases/{id}` with the composed body — pure stdlib urllib, no checkout needed. Idempotency: the appendix always derives from the release action's body output, never the live release body, so any re-run reproduces a byte-identical composed body; on re-dispatch without a new release the gate is false and the step is skipped. FR-023/FR-024 updated.
- Q: What are the `validate-release-note` check semantics? → A: Runs on `opened, reopened, synchronize, edited, labeled, unlabeled, ready_for_review` (labeled/unlabeled are new — applying/removing the skip label must re-report the check); scopes to releasable types only (`feat`/`fix` incl. scoped and `!`-breaking forms, mirroring release-please's releasable rule so the check and the release trigger never disagree); drafts skipped; release-please's own PRs exempt (chore type short-circuits + `autorelease:` label belt-and-suspenders; title from `inputs.pr_title` under the dispatch path, which carries no body); PR body handled via env vars, never shell interpolation. This IS a new required status check name — the landing PR must call out the manual branch-protection addition and create the `release-note/skip` label (verified absent today). FR-022 updated.
- Q: Which PR-discovery algorithm does the release-notes composer use to enumerate PRs since the last tag? → A: The GitHub Compare API (`GET .../compare/{prev_tag}...{new_tag}`, no checkout), never the rendered release-body Markdown links. The composer reads the previous tag from the release action's body output compare-link heading, then extracts each PR number from the trailing `(#N)` on every commit subject in the compare response — the same subject-line parse also yields the conventional-commit type, so only feat/fix commits cost a follow-up `pulls/{N}` fetch to harvest the Release note block, mirroring FR-022's releasable-type scoping. The rendered `(#N)` link markup inside the release body is an internal, overridable release-please rendering detail, not a discovery input; the body output continues to feed only the verbatim appendix (already ratified), never Highlights discovery, so discovery needs no `changelog-notes-type` pin. Because an undiscovered PR cannot reach even the de-prefixed-title fallback, the composer fails loudly — rather than silently dropping the PR — on a Compare API error, a truncated/paginated compare response, or a commit subject with no resolvable trailing `(#N)`, re-targeting the fail-loud check onto the surface that can actually under-enumerate rather than a zero-matches count over changelog markup. Verified live: 22/22 merged commits in this repo carry a trailing `(#N)`; no new permissions are required (`contents: write` and `pull-requests: write` are already declared on `release.yml`). FR-023 updated. Flagged for Plan: first-release (no previous tag) is out of scope, prev-tag resolution assumes today's single release component, and the exact compare-endpoint-to-token-scope mapping is confirmed during implementation.
- Q: What content-sanitization and token-scope hardening govern the release-notes composer, given it turns untrusted PR-body text into a public GitHub Release body? → A: `[security]` consensus, 3/3 (codebase-analyst, spec-context-analyst, domain-researcher; no dissent; operator-ratified 2026-07-08 per the security-override gate). Structural layer: env-var/JSON-only intake (never shell interpolation) matches existing repo precedent exactly and is the documented mitigation for an identical historical failure mode (CVE-2023-34111, a release workflow interpolating PR text into bash); the composer applies the same discipline via GitHub-API JSON harvesting through stdlib `urllib`. Token layer: `contents: write` is both floor and ceiling for the release-body `PATCH` (no narrower built-in scope exists) and is the only permission the composer may hold; the composer runs as its own `release.yml` job with `permissions: {contents: write}` only — never the publishing job's broader inherited `actions: write`/`pull-requests: write` — and the elevated `RELEASE_PLEASE_TOKEN` is explicitly forbidden (its sole purpose is the branch-protection recursion-guard escape). Content layer, deliberately exceeding the raw-HTML-strip already ratified in this session's first clarification (GitHub's own HTML sanitizer does not cover `.atom` feeds, email notifications, or API consumers of the release body): image markdown is stripped entirely (GFM's one allowlisted embedding tag has documented real-world abuse — CamoLeak, CVE-2025-59145 — and no reviewed release note needs an image); leading structural characters (`-`, `*`, `#`) on extracted lines are neutralized so a block cannot inject spurious Markdown structure into the composed body; plain inline links remain permitted as a recorded decision, not an oversight (link-text spoofing is a known residual risk the wider ecosystem generally leaves unrestricted, and stripping links was judged disproportionate given the provenance bound below); blocks are capped at 2,000 characters with a truncate-and-mark fallback (not a check failure), informed by GitHub's 125,000-character release-body ceiling and the Design Concept's Q10 "short block" ratification. Parsing layer: fence extraction is defensive on every harvested PR body regardless of conventional-commit type — FR-022 only shape-checks feat/fix PRs, while the composer harvests every merged PR since the last tag — via a single anchored, CommonMark-nesting-aware fence match (same fence character; closing run no shorter than the opening run), never a partial repair. Threat-model bound: only merged-PR text is ever harvested, and squash-only merges under branch protection mean every harvested body already passed required review — this bounds sanitization to defensive parsing plus the strip/neutralize rules above rather than a full HTML-sanitizer-grade lockdown, avoiding both under- and over-hardening per the constitution's KISS/YAGNI principle. Auditability: neither GitHub's audit log nor Immutable Releases capture release-body edit events, so the `release.yml` run log and job summary — not the release itself — are the durable record of what the composer wrote. FR-021, FR-023, and FR-024 updated.

### User Story 1 - Cross-Platform Python Suite Orchestrator (US1) (Priority: P1)

As a plugin maintainer, I can run the full deterministic test suite through a Python orchestrator that behaves exactly like the previous Bash runner — same flags, same headline output, same exit codes — on any operating system that has Python 3.11+, without needing Bash or `jq`.

**Why this priority**: This is the foundation the entire confinement effort rests on. Until the suite runs from Python, no port can be validated cross-platform and contributors on native Windows cannot run the repo's own gates. It delivers standalone value even before the rest of the stack lands.

**Independent Test**: On a machine with only Python 3.11+ (no Bash, no `jq`), run the orchestrator with `--all`, a single `--layer N`, and the toolchain preflight; confirm the `X/Y passed` headline, layer selection, and exit codes match the recorded Bash-runner behavior.

**Acceptance Scenarios**:

1. **Given** a machine with Python 3.11+ and no Bash available, **When** the maintainer runs the orchestrator with `--all`, **Then** every deterministic layer executes and the run ends with the same `X/Y passed` headline and exit code the Bash runner produced.
2. **Given** the orchestrator, **When** the maintainer passes `--layer N`, `--live`, or the toolchain preflight flag, **Then** each flag selects the same scope the Bash runner selected for that flag.
3. **Given** the shipped runner's suite gate, **When** it resolves which layers exist, **Then** it reads the repo-side suite manifest rather than parsing any Bash runner script, and its existing envelope contract is unchanged.

### User Story 2 - Runtime Count-Parity Proof Per Port (US2) (Priority: P2)

As a reviewer, every port PR shows me a runtime count-parity diff against a committed baseline that proves check names and check counts are preserved 1:1 — so I can trust that porting a layer from Bash to Python lost no coverage.

**Why this priority**: Trust in the migration depends on provable non-regression. Without name-and-count parity a dropped check can hide behind a gained one. This makes each port reviewable in isolation.

**Independent Test**: Take one ported layer, run the committed baseline capture and the new Python module, and confirm the recorded dual-run diff shows an identical ordered check-name inventory and identical runtime count.

**Acceptance Scenarios**:

1. **Given** a port PR, **When** the reviewer reads the PR body, **Then** it contains a dual-run diff comparing the committed baseline (ordered check-name inventory plus runtime count) against the ported module, showing 1:1 preservation.
2. **Given** a port that silently renames or drops a check, **When** the parity comparison runs, **Then** the diff is non-empty and the PR is flagged as a regression rather than passing on an unchanged total count.
3. **Given** the full stack of port PRs, **When** the final parity artifact is produced, **Then** a running count ledger and a suite-parity result record cumulative name-and-count preservation across every ported layer.

### User Story 3 - Repository Bash Confinement Guard (US3) (Priority: P1)

As CI, I fail any PR that introduces a `.sh` file, a Bash-shebang executable, or an active `bash`/`jq` invocation anywhere outside `.github/workflows/`, with a fail-closed allowlist that covers only the vendored upstream `.specify/**` helper files.

**Why this priority**: This is the headline policy of the whole spec. It is the mechanism that makes "repository Bash confined to CI dispatch glue" enforceable and durable rather than a one-time cleanup that erodes over time.

**Independent Test**: Feed the guard three trees — one clean, one with a stray new `.sh` outside the workflow boundary, and one with a non-allowlisted Bash file under `.specify/**` — and confirm it passes the first and fails the other two.

**Acceptance Scenarios**:

1. **Given** a PR that adds a new `.sh` file or an active `bash`/`jq` invocation outside `.github/workflows/`, **When** the confinement guard runs, **Then** the guard fails and the PR is blocked.
2. **Given** the vendored upstream `.specify/**` helpers, **When** the guard runs, **Then** each of the allowlisted files is accepted, marked release-readiness-excluded, and any Bash file appearing under `.specify/**` that is not on the allowlist causes a fail-closed failure.
3. **Given** the release-readiness gate, **When** it evaluates the Bash-free claim, **Then** allowlisted vendored files are excluded from the evidence so they can never satisfy release readiness, and the guard is composed into both CI and the release-readiness gate.

### User Story 4 - Container and Runner Preflight CI (US4) (Priority: P3)

As a maintainer, Linux amd64/arm64 container preflight jobs and Windows x64/ARM64 direct-runner smoke jobs run when runner or gate paths change, Linux results gate merges and Windows results are advisory, and every job uploads an evidence artifact.

**Why this priority**: Preflight raises early confidence that the ported runner behaves across platforms, but it is advisory infrastructure that never substitutes for native operator UAT, so it ranks below the core port and guard.

**Independent Test**: Trigger the preflight workflow via manual dispatch and via a path-filtered change to a runner/gate path; confirm Linux jobs report as required checks, Windows jobs run continue-on-error, and each uploads an availability/smoke evidence artifact.

**Acceptance Scenarios**:

1. **Given** a pull request that changes a runner, gate, or workflow path, **When** CI runs, **Then** the container/runner preflight workflow triggers; a docs-only PR that touches none of those paths does not trigger it.
2. **Given** the preflight jobs, **When** they complete, **Then** the Linux amd64 and arm64 container jobs act as required (gating) checks and the Windows x64/ARM64 smoke jobs run continue-on-error and never block a merge.
3. **Given** a Windows runner label that is unavailable or in public preview, **When** the smoke job runs, **Then** its availability is recorded in the uploaded evidence artifact and no merge is blocked.

As a plugin consumer or evaluator, each GitHub Release opens with plain-English Highlights composed from the release-note blocks that PR authors wrote for consumers, with the raw conventional-commit list preserved below as an appendix — so I can understand what a release actually changed.

**Why this priority**: This closes the deferred "public release notes" scope item and directly serves the marketplace audience, but it is independent of the Bash-confinement mechanics and can land on its own track.

**Acceptance Scenarios**:

1. **Given** a set of feat/fix commits since the last release tag whose PR bodies carry Release note blocks, **When** the release is published, **Then** the GitHub Release body opens with a plain-English Highlights section composed from those blocks.
2. **Given** the same release, **When** a reader scrolls past the Highlights, **Then** the original conventional-commit list is preserved below as an appendix and CHANGELOG.md remains the machine-generated ledger.
3. **Given** the composer, **When** it runs inside the release process, **Then** it uses only deterministic standard-library logic with no LLM calls and no new secrets.

### User Story 6 - Release-Note Enforcement Check (US6) (Priority: P2)

As a PR author, a required check tells me when a feat/fix PR is missing its Release note block, and a `release-note/skip` label lets me exempt a change that has no consumer-visible effect.

**Why this priority**: Enforcement is what keeps US5 durable — an advisory-only convention decays and the composer degrades back to raw commit subjects within a few releases. It is a thin wrapper on US5, so it ranks just after it.

**Independent Test**: Open one feat PR without a Release note block (expect the check to fail), add the block (expect pass), and open another labeled `release-note/skip` (expect pass without a block).

**Acceptance Scenarios**:

1. **Given** a feat or fix PR with no Release note block in its body, **When** the release-note check runs, **Then** the check fails and reports the missing block.
2. **Given** a feat or fix PR that carries a Release note block, **When** the check runs, **Then** it passes.
3. **Given** a PR with no consumer-visible effect labeled `release-note/skip`, **When** the check runs, **Then** it passes without requiring a block.

### Edge Cases

- A `.sh` file or Bash invocation that lives **inside** `.github/workflows/` is the sanctioned dispatch glue and MUST pass the guard.
- A Bash file that appears under `.specify/**` but is **not** on the fail-closed allowlist MUST fail the guard (fail-closed, not fail-open).
- A docs, spec, fixture, or baseline file that merely mentions `bash` or `jq` in prose MUST NOT be treated as an active invocation and MUST pass the guard; a `hooks.json` `command` value or a `package.json` `scripts` value that invokes `bash`/`jq` outside `.github/workflows/` MUST fail it.
- A port that keeps the same total check count but swaps one check name for another MUST be caught by name-level parity, not masked by the unchanged total.
- A layer whose checks are generated in a loop MUST be measured by **runtime** count, not a static grep, so loop-generated checks are counted correctly.
- A feat/fix PR with genuinely no consumer-visible effect MUST be exemptible via `release-note/skip` rather than forced to invent a Release note.
- A release with no PR-authored Release note blocks since the last tag MUST still produce a well-formed Release body (Highlights degrade gracefully; the commit-list appendix is always present).
- A release-notes composer failure that occurs **after** the GitHub Release is already published MUST leave the published release intact with the raw release-please body and surface a red workflow run for visibility, rather than silently shipping an un-composed body or attempting to un-publish; recovery is re-running the failed composer job, not re-dispatching the release workflow (which is gated off when no new release is created).
- A Windows ARM64 runner that is unavailable or in public preview MUST NOT block any merge; its unavailability is recorded as evidence by a mechanism that does not depend on the unavailable runner actually starting (a job whose label has no runner never executes its steps), so unavailability is positively recorded rather than manifesting only as a missing artifact or an indefinitely-queued job (FR-019).
- A ported `.claude/hooks` handler MUST preserve the stdin-JSON / exit-0-or-2 contract even for malformed input, matching its Bash predecessor's behavior.
- A tracked file the confinement guard cannot read or decode (a binary file, or an I/O error) when probing for a Bash shebang MUST be classified by its path suffix alone — never flagged as a false Bash finding and never aborting the scan; the whole-scan fail-closed posture applies only to a missing-git prerequisite, not to an individual unreadable or binary file (FR-002).
- A test module dispatched by the Python orchestrator that crashes (exits nonzero with no `X/Y passed` headline) MUST be recorded as a failure that forces exit 1, distinct from a transitional-skip, so a crash can never masquerade as a green run; a module that exits zero without a headline is a no-summary pass contributing nothing to the counts (FR-006).
- A transient or HTTP GitHub-API failure (network timeout, rate-limit `403`/`429`, or a `5xx` server error) during release-note composition MUST fail loudly with the structured composition-failed diagnostic and a red run — no in-process retry — recovered by re-running the composer job, the same fail-loud disposition as a missing or malformed block (FR-023).

## Requirements *(mandatory)*

### Functional Requirements

#### Confinement policy and guard

- **FR-001**: The repository MUST contain zero `.sh`/`.bash` files and zero Bash-family shebang executables (a `bash` or POSIX `sh` shebang, including bare `#!/bin/sh`) outside `.github/workflows/`, except for an explicit fail-closed allowlist of vendored upstream files. This detection vocabulary is bash-scoped only: `.ps1`, `.bat`, `.cmd`, `.zsh`, and other non-bash-family suffixes or shebangs are outside its scope and require no allowlist entry.
- **FR-002**: A repository-Bash-confinement guard MUST fail any change that introduces a new `.sh` file, a new Bash-shebang executable, or an active `bash`/`jq` invocation outside `.github/workflows/`. Detection surfaces are scoped precisely: (a) the `.sh`-suffix and Bash/POSIX-sh-shebang rules MUST apply repository-wide, including extensionless shebang files; (b) active-invocation-text detection MUST apply only to executable and config-executed surfaces — Python files via AST inspection of `subprocess`/`os.system` call arguments against the prohibited command names, plus structural JSON-value scans of `hooks.json` `command` fields and `package.json` `scripts` values; (c) prose, Markdown, YAML-metadata, fixture, and baseline files MUST NOT be scanned for invocation text — a file that merely mentions `bash` or `jq` MUST NOT be a finding; (d) a Markdown frontmatter path-reference to an allowlisted vendored `.sh` file MUST be governed by that referenced file's own allowlist status (FR-003), not by scanning the referencing document; (e) the Bash-shebang content-probe MUST be robust to unclassifiable content — a tracked file whose first line cannot be read (an I/O error) or cannot be decoded as UTF-8 text (a binary file) yields no Bash shebang and is therefore classified by its path suffix alone, never a scan-aborting error and never a false Bash finding, reusing the guard's established read-first-line primitive whose `OSError`/`UnicodeDecodeError` handling already returns an empty first line; the same content-probe rule governs a symlink whose resolved target is missing or outside the repo root (not content-probed; classified by the tracked link-path suffix per Clarifications Session 2). The whole-scan fail-closed posture is reserved for the missing-git prerequisite (Assumptions), NOT for an individual unreadable or binary file, since flagging every such file as Bash would be a false positive; the path-suffix (`.sh`/`.bash`) rule always applies regardless of readability.
- **FR-003**: The guard MUST maintain a fail-closed allowlist covering exactly the 10 vendored `.specify/**` upstream Spec Kit helper files, each marked `release_readiness_excluded: true`, and MUST fail if any Bash file appears under `.specify/**` that is not on that allowlist. The 4 vendored `.specify/extensions/git/scripts/powershell/*.ps1` counterparts are outside the bash-scoped detection vocabulary defined in FR-001 and are never matched by the guard, so they require no allowlist entry and do not enlarge the count of 10. Because the allowlist schema pins entry count (`minItems`/`maxItems` 10) and path scope (`vendored_specify_helper`) but not path identity, a same-scope SUBSTITUTION — swapping one canonical path for a different `.specify/**/scripts/bash/*.sh` path — would satisfy the schema unchanged; therefore the allowlist's content integrity MUST additionally be asserted by the guard's loader (or a deterministic test) against the enumerated canonical set of exactly the 10 paths listed under Key Entities → Confinement Guard Allowlist, so that broadening or substituting the allowlist file itself is a fail-closed (red) event rather than a change trusted to reviewer vigilance alone. The existing interlock — removing a canonical entry to admit another turns the still-present real vendored `.sh` into a blocking finding — is partial defense that the exact-canonical-set assertion completes for the delete-and-substitute case.
- **FR-004**: Allowlisted vendored files MUST be excluded from release-readiness evidence so they can never satisfy the Bash-free release claim. "Excluded" means excluded from the positive evidence set — the guard surfaces allowlisted entries in an allowlist summary flagged `release_readiness_excluded: true`, and they are never counted as Bash-free evidence — not merely that they do not block. This exclusion MUST be proven, not merely asserted: a deterministic test MUST assert that allowlisted (`release_readiness_excluded: true`) entries can never count as positive Bash-free evidence — the release-readiness Bash-free claim is satisfied only by `blocking_count == 0`, and the mere presence of excluded vendored entries never contributes to a passing claim (mirroring the XPLAT-009 precedent whose guard-result test asserts the allowlist's `release_readiness_excluded` property). This negative control is the provability half of FR-004: without it, "excluded from the positive evidence set" is an unverified property.
- **FR-005**: The guard MUST be composed into both the release-readiness gate and CI so the policy is enforced on every pull request: a `repo_bash_confinement` check in the release-readiness assembly (mirroring the existing zero-bash composition) and a live-scan guard case in the default deterministic suite, riding the existing required checks (the `validate-plugins` sentinel and the release-readiness leg) with no new required status check. The guard case MUST perform a live repository-wide enumeration, never a fixed file list, so newly added files are always scanned. Because this composition is the backstop against future Bash reintroduction, its presence MUST be durable rather than trusted to remain: a deterministic test MUST assert that the `repo_bash_confinement` check remains composed in the release-readiness assembly AND that the confinement guard case remains present in the default deterministic suite roster, so a future edit that silently drops the guard from either surface fails CI (mirroring the XPLAT-009 precedent whose release-readiness test asserts the zero-bash guard is present as exactly one check in the assembly). The FR-007 manifest drift-guard does not cover this — it asserts gate-vs-manifest roster agreement, not the guard case's membership in the default suite nor the check's presence in the release-readiness composition.
- **FR-026**: GitHub Actions workflow shell (`.github/workflows/**`) MUST be limited to CI/CD dispatch glue that invokes the Python runner and gate entrypoints; it MUST NOT embed plugin validation, packaging, install, release, or runtime logic, and MUST NOT shell out to repo-local Bash scripts. This is the affirmative complement to FR-002: FR-002's guard proves no Bash leaks *outside* the workflow boundary (and deliberately exempts `.github/workflows/` from Bash-file detection), while FR-026 keeps the shell *inside* the boundary reduced to dispatch — so the confinement policy is not silently defeated by embedding logic in a workflow `run:` block. The residual `bash tests/speckit-pro/check-toolchain.sh` dispatch step in `pr-checks.yml` is replaced by a direct Python-runner invocation as part of this reduction (delivered in the `pr-checks.yml` dispatch-swap PR — PR 5 of the stack; the self-referential workflow validator is updated in the same PR). That swap replaces a `run:` step inside the existing `test`/`validate-plugins` check surface, not a job name, so it renames no required status check and requires no branch-protection change (contrast PR 11 and PR 12, which do add required checks — see FR-018 and FR-022).

#### Cross-platform suite orchestration

- **FR-006**: Maintainers MUST be able to run the full deterministic suite via a Python orchestrator that preserves the prior runner's flags (`--layer N`, `--live`, `--all`, toolchain preflight), the `X/Y passed` headline output, and exit codes, on any operating system with Python 3.11+ and without Bash or `jq`. This no-Bash/no-`jq` guarantee is the PR-stack **end-state** property, fully realized once PR 10 ports and deletes the last repo-local `.sh`: during the transitional window (PR 2 through PR 9) any layer still carried in the manifest as `shell-legacy-transitional` dispatches its `.sh` predecessor and therefore still requires Bash, so on a Bash-absent platform the orchestrator MUST skip such a layer with an explicit transitional-skip diagnostic (never a silent pass that would report a false green) rather than execute it, while CI — which has Bash throughout the stack — continues to run every layer so per-layer coverage never drops (FR-012). The full no-Bash suite run is therefore complete only from PR 10 onward. The orchestrator's child-outcome disposition mirrors the prior runner 1:1 (research §D5): each dispatched module is read via its `X/Y passed` headline; a module that exits nonzero with no parseable headline — a crash or unhandled error — MUST be recorded as a failure that forces the run's exit 1 (fail-closed), never silently dropped, and is distinct from the transitional-skip above; a module that exits zero without a headline is reported as a no-summary pass contributing nothing to the counts; and the orchestrator's own unhandled error surfaces as a dedicated nonzero exit rather than a false green. Exit codes remain 0 iff no failures, 1 on any failure, 2 on an unknown flag.
- **FR-007**: The suite composition MUST be defined by a single repo-side manifest that is the one source of truth per layer, which both the orchestrator and the shipped runner's suite gate read instead of parsing the former Bash runner. Post-PR-2, the shipped gate's advertised layer roster (`DEFAULT_SUITE`, `EXTENDED_SUITE`, `ALLOWED_LAYERS`) MUST be derived solely from the manifest, failing closed when the manifest is absent or unreadable; a deterministic drift-guard test MUST assert the gate's advertised roster and dispatch kinds match the manifest exactly. Because that drift-guard asserts gate-vs-manifest agreement only, two manifest-integrity invariants MUST be enforced independently of it: (a) every layer's `scripts[].path` MUST resolve to an existing repository file, so a stale entry can never dispatch a deleted script; and (b) no layer may carry `dispatch: shell-legacy-transitional` after PR 10 — that dispatch kind is valid only between PR 2 and a layer's own port-PR boundary, and its terminal absence MUST be asserted (not merely documented) so a transitional entry cannot silently persist once the confinement guard is active.
- **FR-008**: The shipped runner's suite gate MUST continue to honor its existing envelope contract while sourcing layer composition from the manifest; any change to shipped-runner bytes MUST follow the payload/proof regeneration ritual. Each layer's native internal gate implementation (for example `check_layer5`, `check_layer7`, `check_layer8`) MUST be retired at the PR that ports the corresponding layer to a manifest-named Python module, so each layer has exactly one implementation of record, named by the manifest; a permanent equivalence shim between a retired native check and its ported replacement MUST NOT be kept.

#### Port fidelity and count parity

- **FR-009**: All active repo-local tooling — test-harness modules, `scripts/**` helpers, `.claude/hooks/**`, and the live-AI eval runners for Layers 2/3/6 — MUST be ported to Python 3.11+ standard library only, with no new runtime dependency.
- **FR-010**: Ported test modules MUST follow the house convention: `unittest`, a custom `__main__` printing `<label>: {passed}/{total} passed`, and one counted Python unit per former assertion execution — not per former `set_test`. The counted unit is every former `assert_*`/`_pass`/`_fail` execution: this covers both loop-generated repetitions and non-loop multi-assertion groupings, not merely loop iterations. Each former assertion execution MUST map to exactly one counted Python unit and count as 1 toward `total`; a non-loop former assertion may be its own test method or a `subTest` unit, while a loop-generated assertion execution MUST be a `subTest`.
- **FR-011**: Each port PR MUST demonstrate 1:1 preservation of check names and runtime counts against a committed baseline (ordered check-name inventory plus runtime count, with names captured verbatim from runtime PASS/FAIL output rather than reconstructed from source literals), with the dual-run diff recorded in the PR body.
- **FR-012**: Each port PR MUST land the port, the manifest update, and the corresponding `.sh` deletion together (same-PR swap) so no layer ever runs with zero coverage.
- **FR-013**: A running count ledger and a final suite-parity result MUST record cumulative name-and-count parity evidence across the PR stack.
- **FR-014**: Ported `.claude/hooks/**` handlers MUST preserve the stdin-JSON / exit-0-or-2 hook contract. Beyond that I/O contract, the ported handlers MUST parse their stdin payload via the Python standard-library `json` module and MUST NOT shell-interpolate any of that untrusted input into a subprocess or shell command — the same env-var/JSON-only untrusted-input discipline the release-notes composer follows (FR-023), replacing the predecessor's `jq` extraction with stdlib `json` (research §D12) so the hook intake stays off the shell-injection surface even while the hooks remain unwired today.
- **FR-015**: Ported live-AI eval runners (Layers 2/3/6) MUST preserve their CLI argument contracts and codex staging semantics.

#### Container and runner preflight CI

- **FR-017**: A container/runner preflight workflow MUST run on path-filtered pull requests (runner, gate, and workflow paths) and on manual dispatch, and MUST NOT run on changes that cannot affect the runner (for example, docs-only PRs). The new `container-preflight.yml` workflow MUST declare a least-privilege permissions posture matching the repository convention already established in `pr-checks.yml` and `deploy-docs.yml` — a workflow-level `permissions: {}` default with each job granting only the minimal scope it needs (`contents: read` for the checkout of runner/gate paths; the evidence-artifact upload uses the built-in token and needs no broader grant) — so a new CI surface never quietly widens the repository's token exposure.
- **FR-018**: Linux amd64 and arm64 container preflight jobs MUST act as required (gating) checks on the paths that trigger them. Because these are NEW required status check names and GitHub does not auto-register required checks (a renamed or newly-added check silently leaves branch protection vacuous until updated manually), the PR that lands them (PR 11) MUST call out the manual branch-protection addition of the two Linux check names — the same explicit branch-protection callout FR-022 requires for `validate-release-note`. This keeps the stack's branch-protection-change ledger complete: PR 5's dispatch swap is required-check-neutral (see FR-026), PR 10's guard adds no required check (see FR-005), PR 11 adds the two Linux checks (here), and PR 12 adds `validate-release-note` (FR-022).
- **FR-019**: Windows x64 and ARM64 direct-runner smoke jobs MUST run as advisory (continue-on-error), never blocking merges, with runner availability recorded per label. Because a job whose requested runner label is unavailable or in public preview does not execute its steps — it waits for a runner that does not exist rather than running — the per-label availability determination MUST be recorded by a mechanism that does not depend on the scarce Windows runner actually starting, so an unavailable or public-preview label yields a positively-recorded `available: false` result rather than only a missing artifact or an indefinitely-queued job, and the advisory (continue-on-error) framing MUST ensure such a job never leaves the workflow blocked.
- **FR-020**: The preflight jobs MUST upload evidence artifacts, and their results MUST NOT be treated as native installed-plugin UAT evidence. The evidence-artifact upload MUST run regardless of the gated entrypoint step's outcome (always-run semantics, matching the existing `pr-checks.yml` `if: always()` artifact-upload convention) so that a FAILING preflight still captures its evidence rather than skipping the upload; a gating Linux job's merge-blocking verdict derives from the entrypoint checks themselves, and an evidence-upload problem is surfaced without silently masking an entrypoint failure or flipping a passing gate.
- **FR-027**: The container/runner preflight jobs MUST exercise the same Python runner and release-gate entrypoints CI uses — the runner toolchain preflight, the deterministic suite gate, the no-Bash/`jq` confinement guard, and the relevant release-readiness checks — rather than a divergent or reduced code path, so preflight evidence reflects the same behavior a release gate would observe. The Linux `amd64`/`arm64` container jobs run these entrypoints as gating checks (FR-018); the Windows `x64`/`ARM64` smoke jobs run the interpreter-discovery and runner `runtime-info`/`preflight` subset advisorily (FR-019). Without this fidelity requirement a trivial preflight job would satisfy FR-017/FR-018/FR-020 while proving nothing about cross-platform runner behavior.

#### Public release notes

- **FR-021**: Each feat/fix PR MUST carry a consumer-facing Release note block in its body: exactly one fenced code block whose info-string is `release-note`, containing multiline plain-English prose written for consumers. Allowed inline markdown is an explicit subset — emphasis, plain inline links, and `-` bullets; the composer strips raw HTML entirely, strips image markdown entirely (GFM's `![...]()` syntax carries no legitimate use in a consumer-facing note), and neutralizes leading structural characters (`-`, `*`, `#`) on extracted lines so a block's content cannot inject spurious Markdown structure into the composed release body; a block longer than 2,000 characters is truncated by the composer with a truncation marker rather than failing the check; empty or whitespace-only counts as missing; zero or more-than-one block fails the check. A `.github/pull_request_template.md` seeds the empty block under a `## Release note` heading.
- **FR-022**: A required `validate-release-note` check MUST fail feat/fix PRs missing the Release note block, and a `release-note/skip` label MUST exempt changes with no consumer-visible effect. The check runs on `opened, reopened, synchronize, edited, labeled, unlabeled, ready_for_review` events so body edits and label changes re-report; it scopes to releasable conventional-commit types only (`feat`/`fix`, including scoped and `!`-breaking forms — `chore`/`docs`/`refactor`/`test` pass trivially); draft PRs are skipped; release-please's own PRs are exempt (chore type short-circuits, plus the `autorelease:` label as belt-and-suspenders, with the title read from `inputs.pr_title` under the dispatch path); ALL untrusted text the check consumes — the `pull_request`-event PR body AND the `workflow_dispatch`-path `inputs.pr_title` — is passed via environment variables and never interpolated into shell, so neither event path exposes a shell-injection surface. This is a NEW required status check name — the PR that lands it MUST call out the manual branch-protection update adding `validate-release-note`, and MUST create the `release-note/skip` label.
- **FR-023**: At release publication, a deterministic Python standard-library composer MUST rewrite the GitHub Release body to open with plain-English Highlights composed from the PR-authored Release note blocks harvested for all commits since the last tag, preserving the conventional-commit list below as an appendix. PR discovery for Highlights MUST enumerate commits since the last tag via the GitHub Compare API (`GET .../compare/{prev_tag}...{new_tag}`, no checkout — the previous tag read from the release action's body output compare-link heading), extracting each PR number from the trailing `(#N)` on every commit subject; the composer MUST NOT parse the release body's rendered Markdown links to discover PR numbers, since that link markup is an internal, overridable release-please rendering detail — the body output feeds only the verbatim appendix, never Highlights discovery. Fallback rules: a `release-note/skip`-labeled PR is omitted from Highlights (it still appears in the appendix); a feat/fix PR missing a block without the skip label degrades to its de-prefixed PR title; when zero PRs in the range carry blocks, Highlights degrade to de-prefixed subjects and the appendix is always present. Because an undiscovered PR cannot reach any of the Fallback rules above — it never even surfaces as a de-prefixed-title placeholder — the composer MUST fail loudly, never silently under-enumerate, on a Compare API error, a truncated or paginated compare response, or a commit subject with no resolvable trailing `(#N)`. The composer runs as its own `release.yml` job (per FR-024) gated on the release-created output, resolves the release ID by tag (`GET .../releases/tags/{tag}` — the release action exposes no ID output) then `PATCH`es the release body, and is idempotent: the appendix is always derived from the release action's body output, never from the live release body, so re-runs reproduce a byte-identical composed body. Harvesting is not limited to feat/fix PRs: FR-022 only shape-gates feat/fix PRs, while the composer harvests Release note blocks from every merged PR since the last tag regardless of conventional-commit type, and because merges are squash-only under branch protection, every harvested PR body has already passed required review — bounding the threat model the composer's parsing must defend against. Extraction MUST therefore be defensive on every harvested body: a single anchored, CommonMark-nesting-aware fence extractor (matching fence character; closing run length no shorter than the opening run) requiring exactly one match, treating zero or ambiguous matches the same as a missing block above, and never attempting partial repair of a malformed fence. PR bodies are harvested via the GitHub API as JSON field values through the same pure-stdlib `urllib` calls used for the tag-resolution and `PATCH` above, never via shell text substitution or git-log parsing, matching the repository's existing environment-variable/JSON-only intake convention for untrusted PR text. Because the composed release body is not a repository file and nothing downstream re-parses or re-verifies it, the composer MUST emit its own structured diagnostic (for example, a `release_note_composition_failed` outcome) on any composition failure rather than relying on external verification; and because neither the GitHub audit log nor Immutable Releases capture release-body edit events, the `release.yml` run log and job summary are the durable record of what the composer wrote. Because the composer runs only after publication (FR-024's `needs:` ordering), a composer-job failure MUST NOT un-publish or block the already-created GitHub Release — the release stands with release-please's raw body — but the composer job MUST surface the failure as a red workflow run so an un-composed body is noticed rather than silently shipped; the recovery path is re-running that failed run's composer job (which replays with the original release-created context intact), never a fresh `release.yml` dispatch, which the release-created gate skips when no new release exists. The fail-loud disposition extends beyond the three discovery triggers above to every transient or HTTP-level failure on any of the composer's three GitHub API calls (the Compare walk, the tag-to-release-ID resolution, and the release-body `PATCH`): a network timeout, a connection error, an HTTP rate-limit response (GitHub returns `403` or `429` for primary and secondary limits), or an HTTP `5xx` server error MUST be treated as a composition failure — the same `release_note_composition_failed` structured diagnostic and red run — with NO in-process retry or backoff, recovered by re-running the failed composer job, mirroring the repository's existing transient-`api.github.com` recovery convention of re-running the job rather than adding retry logic.
- **FR-024**: The release-notes composer MUST make no LLM calls and require no new secrets — it reuses the built-in workflow token under the existing `contents: write` permission; CHANGELOG.md MUST remain the machine-generated ledger. The composer MUST run as its own `release.yml` job (declared with `needs:` on the publishing job, gated on the release-created output) carrying only `permissions: {contents: write}` at the job level, never inheriting the publishing job's broader `actions: write` / `pull-requests: write` grants — matching the repository's existing least-privilege convention of workflow-level `permissions: {}` plus per-job declarations. `contents: write` is both the floor and the ceiling for the release-body `PATCH` call: no narrower built-in scope exists, and the composer MUST NEVER use the elevated `RELEASE_PLEASE_TOKEN`, which exists solely to escape the branch-protection recursion guard on release-please PR checks and MUST NOT be repurposed for release-body writes.

Toolchain preflight carries `counted_in_total: false`.
- **Confinement Guard Allowlist**: The fail-closed list of the 10 vendored `.specify/**` upstream files, each flagged `release_readiness_excluded: true`. Contract (per Clarifications Session 2): rhymes with the XPLAT-009 historical-allowlist schema — top-level `{schema_version, feature_id, entries[]}`, per entry `{path, categories[], reason, scope, release_readiness_excluded: true}` with `additionalProperties: false` and `release_readiness_excluded` required on every entry; the loader accepts only a `vendored_specify_helper` path scope (`.specify/scripts/bash/**` and `.specify/extensions/**/scripts/bash/**`) and pins all 10 paths as individual entries (no globs): `.specify/extensions/git/scripts/bash/{auto-commit,create-new-feature,git-common,initialize-repo}.sh` and `.specify/scripts/bash/{check-prerequisites,common,create-new-feature,setup-plan,setup-tasks,update-agent-context}.sh`. Any `.sh` or Bash-shebang file under `.specify/**` not on the list fails closed.
- **Count-Parity Baseline**: A committed per-script capture at the fixed path `tests/speckit-pro/parity/bash-to-python/<script>-baseline.txt` recording the ordered check-name inventory and runtime count used to prove 1:1 preservation on each port. Runtime count (per Clarifications Session 1) is measured per assertion execution — every former `assert_*`/`_pass`/`_fail` call, covering both non-loop multi-assertion grouping and loops — not per former `set_test`. Frozen format: one line per executed `_pass`/`_fail` call in execution order, `NNN <canonical-name>` (grouped checks legitimately repeat the same name on consecutive lines — up to 11 observed in this repo), then a trailing `TOTAL: <N>` line where `N = PASS_COUNT + FAIL_COUNT`. Check names are captured VERBATIM from runtime `VERBOSE=true` PASS/FAIL output — never reconstructed from source literals, since loop- and data-driven names only exist at runtime — via a capture filter that parses only lines matching `^\s*(.+?)\s\.\.\.\s(PASS|FAIL)$` and discards all other subprocess stdout (interleaving is possible mid-line). The capture environment is pinned and recorded (non-root, matching CI — a root-vs-non-root capture of `test-moc-lint-exit-codes.sh` diverges 31 vs. 36 assertions). A script with more than one invocation mode (e.g., `validate-moc-orphan.sh`'s optional scan-root argument, which changes assertion count from 29 to 0) gets one committed baseline file per (script, invocation-mode) pair rather than a single shared file. Regeneration triggers include not only script-source changes but also changes to any data file the script enumerates at runtime (e.g., `validate-curated-set.sh` check names are driven by live `scripts/curated-set.json` content). Capture tooling SHOULD fail loudly on any PASS/FAIL line with an empty or stale name rather than silently falling back to a positional `check-NNN` placeholder (recommended safeguard; the census found zero un-named executions, so a positional-fallback feature itself is not warranted). Beyond recording the capture environment, the environment pin MUST be enforced on BOTH sides of the parity proof: the baseline capture AND the port-side parity comparison run in the same pinned (non-root, CI-matching) environment, and the capture records that environment alongside the baseline, so a root-vs-non-root drift (the 31-vs-36 divergence noted above) surfaces as a loud parity failure or a visible environment mismatch rather than a silently divergent count of record.
- **Count Ledger / Suite-Parity Result**: The running and final cumulative parity evidence across the PR stack.
- **Disposition Ledger**: The committed record of the 34 deleted orphan Bash tests and the rationale for deleting rather than porting each.
- **Release Note Block**: The consumer-facing block each feat/fix PR carries in its body, harvested by the composer at release time. Grammar (per Clarifications Session 3): exactly one fenced code block with info-string `release-note`, identified by CommonMark-nesting-aware fence matching; multiline plain-English prose; inline markdown limited to emphasis, plain inline links, and `-` bullets; raw HTML and image markdown stripped at composition, with leading structural characters (`-`, `*`, `#`) on extracted lines neutralized; blocks capped at 2,000 characters (truncate-and-mark, not a failure); empty/whitespace-only counts as missing; skip is expressed only by the `release-note/skip` label, never by an in-block sentinel.
- **Container-Preflight Evidence Artifact**: The per-platform availability and smoke-result artifact uploaded by the preflight jobs.
- **Spec-Size Estimate**: The `{estimated_loc, suggested_slices, status}` result the restored `estimate-spec-size` operation returns.

## Assumptions

- Python 3.11+ is available in CI and on maintainer machines (already required by the existing runner), so it is the only runtime the ported tooling may depend on.
- `git` is available and the repository is a proper checkout wherever the confinement guard runs (CI and maintainer machines — already a toolchain prerequisite of the existing runner); the guard fails closed with a missing-prerequisite diagnostic when git is unavailable, never silently passing.
- `.github/workflows/**` remains the single sanctioned home for Bash dispatch glue, per the cross-platform roadmap policy.
- The 10 vendored `.specify/**` upstream Spec Kit helper files are stable and are not modified or forked by this spec; they are documented-and-guarded, not ported.
- The test suite continues to live at the repository root (`tests/speckit-pro/`), a sibling of the plugin, because plugin install copies the whole plugin directory; this spec does not relocate it.
- GitHub API access is available at release time so the composer can harvest PR bodies for commits since the last tag; when no Release note blocks are found, the Highlights section degrades gracefully and the commit-list appendix is always present.
- Windows runner availability (especially ARM64/`windows-11-arm`) may vary; the advisory, continue-on-error framing accommodates unavailable or public-preview states.
- XPLAT-009 already completed plugin-source and generated-payload Bash removal; XPLAT-008 native operator UAT remains the release-claim gate, and this spec's container/runner preflight is preflight-only evidence that never substitutes for it.
- The `estimate-spec-size` restoration matches the input/output contract the grill-me and speckit-prd skills already expect, since those skills are the callers that lost the estimator when its Bash predecessor was deleted.
