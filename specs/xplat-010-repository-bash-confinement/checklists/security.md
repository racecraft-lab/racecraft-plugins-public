# Security Quality Checklist: Repository Bash Confinement and CI Dispatch Guard

**Purpose**: Validate the *security-seam* requirements before implementation — the tamper-resistance of the confinement allowlist, the provable exclusion of allowlisted entries from release evidence, the durability of the guard as the backstop against future Bash reintroduction, the release-notes composer's token scope and PR-text injection safety, and the least-privilege / untrusted-intake posture of the new preflight workflow and ported hooks
**Created**: 2026-07-09 by `/speckit-checklist security` (autopilot Phase 4, domain 4 of 4)
**Feature**: [spec.md](../spec.md)
**Validates**: spec.md + plan.md together (post-Plan), with `contracts/` as supporting evidence. This is a security-quality checklist ("unit tests for the requirements' trust boundaries"), distinct from the requirements-quality checklist in [requirements.md](./requirements.md), the integration-quality checklist in [integration.md](./integration.md), and the reliability-quality checklist in [reliability.md](./reliability.md); all four coexist per the `/speckit-checklist` append convention.

**Domain focus** (from the workflow prompt): (1) allowlist entries cannot be broadened silently (fail-closed loader, per-file pins); (2) `release_readiness_excluded` entries provably cannot satisfy release gates; (3) composer token scope (`contents: write` only) and injection-safety of PR-body text into the release body; (4) the guard remaining the backstop against future Bash reintroduction. Probed beyond the operator-ratified Session-3 composer set: allowlist-loader tamper-resistance, `release_readiness_excluded` provability, guard-composition durability, `container-preflight.yml` least-privilege permissions, hooks intake safety, and the `validate-release-note` `workflow_dispatch` injection surface.

## A. Confinement Guard Allowlist — Tamper Resistance & Fail-Closed Scope

- [ ] CHK001 Are the allowlist's anti-broadening controls specified — per-file pins (no globs), `additionalProperties: false`, exactly 10 entries (`minItems`/`maxItems`), and a `vendored_specify_helper` path-scope predicate that structurally rejects any path outside `.specify/scripts/bash/**` and `.specify/extensions/**/scripts/bash/**`? [Completeness, Spec §FR-003, §Key Entities: Confinement Guard Allowlist, Contract confinement-allowlist.schema.json]
- [x] CHK002 Is CHANGING the allowlist file itself a guarded event — does a requirement mandate that the loader (or a deterministic test) asserts the entry set equals the enumerated canonical 10 paths, so SUBSTITUTING one canonical path for a different in-scope `.specify/.../bash/*.sh` path — which passes the count + scope schema unchanged — is caught fail-closed rather than left to reviewer vigilance alone? [Resolved → Spec §FR-003] (Previously gap-marked: the ratified schema pins entry count (`minItems`/`maxItems` 10), `additionalProperties: false`, and the `vendored_specify_helper` path scope, but NOT path identity — so a same-scope substitution satisfies the schema unchanged and broadening the allowlist file was guarded only by reviewer vigilance. Remediated by extending **FR-003** — the allowlist's content integrity MUST be asserted by the loader or a deterministic test against the enumerated canonical set of exactly the 10 paths, so broadening/substituting the allowlist file itself is a fail-closed/red event; the existing delete-makes-blocking interlock is recorded as partial defense the exact-set assertion completes. Grounded in the confinement-allowlist schema count+scope pins, the data-model §2 canonical enumeration, and the guard's fail-closed non-allowlisted-`.specify`-Bash rule.) [Coverage, Spec §FR-003, Contract confinement-allowlist.schema.json]
- [ ] CHK003 Is the fail-closed disposition specified for any `.sh`/Bash-shebang file appearing under `.specify/**` that is not on the allowlist (a blocking finding, never fail-open)? [Coverage, Spec §FR-003, §Edge Cases]
- [ ] CHK004 Is it specified that the 4 vendored `.ps1` counterparts are outside the bash-scoped detection vocabulary (never matched), so the allowlist cannot be enlarged to admit non-Bash executables and the count stays exactly 10? [Consistency, Spec §FR-001, §FR-003, §Clarifications Session 2]

[Resolved → Spec §FR-004] (Previously gap-marked: FR-004 stated the exclusion property and the result schema encodes `release_readiness_excluded: const true`, but no requirement mandated a test PROVING excluded entries never count as positive evidence. Grounded in the XPLAT-009 guard-result test that already asserts the allowlist's `release_readiness_excluded` property (`test-speckit-pro-gates.py`) and Constitution Principle IV (test coverage before merge).) - [x] CHK006 Does a requirement mandate a deterministic assertion that the `repo_bash_confinement` check STAYS composed into the release-readiness assembly AND the confinement guard case STAYS present in the default deterministic suite, so a future PR cannot silently drop the backstop (the FR-007 drift-guard asserts only gate-vs-manifest agreement, which covers neither release-readiness composition nor guard-case membership)? [Resolved → Spec §FR-005] (Previously gap-marked: FR-005 stated the guard IS composed into release-readiness and the default suite, but nothing asserted it STAYS composed — the durability of the backstop was trusted, and the FR-007 drift-guard's gate-vs-manifest scope covers neither surface. Remediated by extending **FR-005** — a deterministic test MUST assert the `repo_bash_confinement` check remains in the release-readiness assembly and the guard case remains in the default-suite roster, so a silent drop from either surface fails CI. - [ ] CHK008 Is the guard's enumeration specified as a live repository-wide `git ls-files -z` scan (never a fixed file list) so newly added files are always scanned? [Coverage, Spec §FR-005, Contract repo-bash-confinement-result.schema.json]

- [x] CHK018 Does a requirement mandate that the NEW `container-preflight.yml` declares a least-privilege permissions posture (workflow-level `permissions: {}` with each job granting only the minimal scope it needs — `contents: read` for checkout), matching the repository convention already established in `pr-checks.yml` and `deploy-docs.yml`? [Resolved → Spec §FR-017] (Previously gap-marked: FR-017–020/027 specified the preflight workflow's triggers, gating, evidence, and entrypoint fidelity but never its token/permissions posture — a new CI workflow could ship with default-broad permissions. Remediated by extending **FR-017** — the new workflow MUST declare workflow-level `permissions: {}` with per-job minimal `contents: read` (artifact upload uses the built-in token), matching the repo convention. Grounded in `pr-checks.yml` (workflow-level `permissions: {}` + per-job `contents: read`) and `deploy-docs.yml` (the same least-privilege pattern on a comparably new workflow).) [Resolved → Spec §FR-014] (Previously gap-marked: FR-014 required the stdin-JSON / exit-0-or-2 I/O contract but not the intake SAFETY — the security property "parse via stdlib json, never shell-interpolate untrusted input" lived only in research §D12 as a port-mechanics note, an asymmetry with the composer's explicit FR-023 discipline. Remediated by extending **FR-014** — the handlers MUST parse stdin via stdlib `json` and MUST NOT shell-interpolate the untrusted payload, the same env-var/JSON-only discipline as FR-023.
