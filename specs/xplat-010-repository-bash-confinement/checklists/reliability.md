# Reliability Quality Checklist: Repository Bash Confinement and CI Dispatch Guard

**Purpose**: Validate the *reliability-seam* requirements before implementation — the fail-closed vs fail-open disposition of every new gate (confinement guard, suite orchestrator, release-notes composer, container/runner preflight, count-parity capture, spec-size estimator) under ambiguous input, missing prerequisites, and transient failure
**Created**: 2026-07-08 by `/speckit-checklist reliability` (autopilot Phase 4, domain 3 of 4)
**Feature**: [spec.md](../spec.md)
**Validates**: spec.md + plan.md together (post-Plan), with `contracts/` as supporting evidence. This is a reliability-quality checklist ("unit tests for the requirements' failure modes"), distinct from the requirements-quality checklist in [requirements.md](./requirements.md) and the integration-quality checklist in [integration.md](./integration.md); all three coexist per the `/speckit-checklist` append convention.

**Domain focus** (from the workflow prompt): every new gate's fail-closed vs fail-open choice stated explicitly — (1) guard classification of ambiguous files (binary, unreadable, extensionless, symlink); (2) git-unavailable / not-a-checkout fail-closed path; (3) composer fallback on missing/malformed/skip blocks AND on transient GitHub-API failure; (4) Windows runner-label unavailability recorded without failing the workflow; (5) run-all.py exit-code taxonomy on a crashed vs check-failing module; (6) baseline capture environment drift; (7) preflight evidence-upload failure; (8) estimator malformed size signals; (9) manifest integrity.

- [ ] CHK012 Is the composer's Highlights fallback specified for a missing block on a feat/fix PR without the skip label (degrade to de-prefixed PR title), a malformed or ambiguous fence (treated identically to missing, never partial-repaired), and a `release-note/skip`-labeled PR (omitted from Highlights, retained in the appendix)? [Coverage, Spec §FR-023, Contract release-note-block.contract.md §4]
- [ ] CHK013 Is the zero-blocks-in-range case dispositioned (all Highlights degrade to de-prefixed subjects; the commit-list appendix is always present)? [Edge Case, Spec §FR-023, §Edge Cases]
- [x] CHK014 Is the composer's disposition specified for TRANSIENT / HTTP GitHub-API failures — connection timeout, HTTP 5xx, and 403/429 rate-limiting — on ANY of its three API calls (compare, tag-resolution, body PATCH), and is retry-vs-no-retry stated, rather than only the three enumerated discovery triggers (compare error / truncated-paginated response / unresolvable trailing `(#N)`)? [Resolved → Spec §FR-023, §Edge Cases] (Previously gap-marked: FR-023's fail-loud rule enumerated only three discovery triggers and left transient/HTTP failures to the generic "any composition failure" catch-all, with retry-vs-no-retry unstated. Remediated by extending **FR-023** — a network timeout, connection error, rate-limit `403`/`429`, or `5xx` on any of the three API calls is a fail-loud composition failure with NO in-process retry, recovered by re-running the composer job, mirroring the repository's transient-`api.github.com` re-run convention (GitHub REST rate-limit status codes per GitHub Docs) — plus an **Edge Cases** bullet.) [Edge Case, Spec §FR-023]
- [ ] CHK015 Is a post-publication composer-JOB failure dispositioned (the published release stands with release-please's raw body; a red run surfaces the failure; recovery is re-running the composer job, never a gated-off fresh `release.yml` dispatch)? [Edge Case, Spec §FR-023, §Edge Cases]
- [ ] CHK016 Is composer idempotency specified so a re-run reproduces a byte-identical body (the appendix always derives from the release action's body output, never from the live release body)? [Completeness, Spec §FR-023]

Remediated by extending **FR-020** — the upload runs regardless of the entrypoint outcome (always-run, matching the existing `pr-checks.yml` `if: always()` convention) so a failing preflight still captures evidence; the Linux gate verdict derives from the entrypoint checks, and an upload problem neither masks an entrypoint failure nor flips a passing gate.)
