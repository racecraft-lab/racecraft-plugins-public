# UX Checklist: Scaffold Integration — blind-spot pass and autopilot chain

**Purpose**: Requirements-quality validation of the operator's experience end to end — the findings presentation, the single confirmation, the two reports and their relationship, the branch points the run can take, and whether the operator can tell at every stage what just happened and what happens next.
**Created**: 2026-08-12
**Feature**: [spec.md](../spec.md) · [plan.md](../plan.md) · [contracts/blind-spot-pass.md](../contracts/blind-spot-pass.md) · [contracts/chain-handoff.md](../contracts/chain-handoff.md)

**Note**: This checklist is generated by the `/speckit-checklist` command based on feature context and requirements. It tests whether the requirements are written well enough to implement without interpretation — not whether an implementation works.

**Depth**: formal release gate. **Audience**: reviewer at PR time, plus the `tasks.md` generator and the UAT runbook author.

**Relationship to the two prior domains**: api-contracts closed the wait deadline, the three-outcome classification, the pre-chain predicate, the heading vocabulary, and the resume command. error-handling closed the durable record's writer, the degraded-seeding path, the three no-chain endings, and the completion test. Both are re-verified here as passing rather than re-litigated. This domain spends its effort on the one subject neither reached: what the operator sees, in order, and whether it is enough.

## Exactly One Confirmation

- [x] CHK009 - Is SC-007's "at most one confirmation outside the interview" true against the shipped scaffold text it will be measured on? Both variants already stop for **explicit operator approval** before running documented bootstrap commands at Step 3.5, and the Claude variant additionally **asks the user whether to reuse or recreate** an existing worktree at Step 3. On this repository — whose root `AGENTS.md` documents a Worktree Preflight — the ordinary run therefore asks at least twice outside the interview, and the chain confirmation is not the first. The criterion is stated as a measurable outcome and is falsified as written. [Resolved] [Spec §SC-007, §FR-013]
- [x] CHK010 - Is the universe SC-007 counts stated explicitly, so "at most one" is measurable rather than aspirational? Without a named universe an implementer cannot tell whether a bootstrap approval, a reuse question, or a failure-handling stop counts against the budget, and the phrase reads as headroom a later change may spend rather than as a cap on this feature's own additions. [Resolved] [Spec §SC-007, Contract chain-handoff §4]
- [x] CHK011 - Is the budget stated in all three of its states — exactly one when the chain is attempted, none when the FR-013a check fails, never more? [Measurability, Spec §SC-007, Contract chain-handoff §4]
- [x] CHK012 - Is the confirmation fully specified — mechanism per platform, exact question text, option count, option order, mutual exclusivity? [Completeness, Spec §FR-013, Contract chain-handoff §4] *(closed by the api-contracts domain; re-verified here)*
- [x] CHK013 - Is FR-011 stated strongly enough that the findings stage cannot acquire a prompt — no confirmation, no curation step, no continue/abort? [Clarity, Spec §FR-011, Contract blind-spot-pass §10]
- [x] CHK014 - Is a free-text confirmation fallback excluded, so an absent structured mechanism cannot be answered by parsing prose? [Completeness, Spec §FR-015b, Contract chain-handoff §4]
- [x] CHK015 - Is SC-011 scoped to the flow this feature specifies? As written it invites "a reader comparing the two platform variants" to find no behavioural difference beyond four named ones, but the shipped files already differ outside that list on a subject this feature touches: Claude asks before reusing an existing worktree while Codex reuses without asking. The criterion is unfalsifiable against pre-existing text it never intended to cover. [Resolved] [Spec §SC-011, §FR-022]

## The Two Reports And What Passes Between Them

- [x] CHK025 - Is the boundary between the two reports stated, so the closing report is not merely the first one printed again? On the decline path the closing report's artifact index restates paths the Scaffold Complete report listed a screen earlier, and its `Next step` restates that report's `Ready to run:` command. Nothing anywhere states what the closing report adds that the first cannot, so the requirement as written produces exactly the redundancy that trains an operator to skim the report carrying the outcome. [Resolved] [Spec §FR-016, §FR-017, §FR-018, Contract chain-handoff §1, §8.3]
- [x] CHK026 - Do the two reports give the operator the **same** command for the same action? The Scaffold Complete report prints `/speckit-pro:speckit-autopilot <workflow-file>` with no stage token, while FR-014 and contract §5 fix the hand-off and chain form as `... --stage plan`. The operator is shown two different commands for one action, one screen apart, and nothing reconciles them. [Resolved] [Spec §FR-013, §FR-014, §FR-015, Contract chain-handoff §5]
- [x] CHK027 - Is the Scaffold Complete report's `Ready to run:` instruction reconciled with the confirmation that immediately follows it? FR-013 already identified this exact conflict class and fixed one half of it, softening `Review both files first` so the report and the confirmation stop giving opposite instructions. The other half was not fixed: the report tells the operator to run a command, and scaffold then offers to run it for them. [Resolved] [Spec §FR-013, §FR-016, Contract chain-handoff §4]
- [x] CHK028 - Is the ordering of the two reports fixed **per platform**, with the reason the pre-existing one comes first? [Completeness, Spec §FR-016, §FR-017, Contract chain-handoff §1] *(closed by the api-contracts domain; re-verified here)*
- [x] CHK029 - Is "printed, not written to a file" stated as a requirement rather than left to the reader of the layout block? [Clarity, Spec §FR-017]
- [x] CHK030 - Is the set-aside findings count excluded from the closing report explicitly, with its actual home named, so its absence does not read as an omission? [Consistency, Spec §FR-018, Contract chain-handoff §8]
- [x] CHK031 - Is the draft-PR line's absent-PR wording given literally, and is it worded so a reader does not mistake an expected absence for a failure? [Clarity, Spec §FR-018, §SC-008, Contract chain-handoff §8.1]
