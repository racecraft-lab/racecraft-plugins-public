        About this demo
        
      
        Design simulation — no real approval authority or security qualification
        All plan defects, repairs, reports, reviewer records and task starts are simulated. Buttons prove no real human presence or signing authority.
        
      
        What this explores
        Can an operator request corrections, compare a revised plan with planning evidence, and approve only when every issue is fixed and checked?
        
      
        The example is grounded in ADR 0012. It does not report actual repository defects or passing tests. The stricter demo profile replaces residual acceptance for this interface; accepted ADR 0013 and shipped runtime remain unchanged.
        
      
        Copy-and-paste handoffs
        The interface prepares prompts for your current Claude Code or Codex session. It sends no message, spawns no session and starts no work. Load example revised plan demonstrates a returned package.
        
      
        Planning checks compare the example plan declarations with ADR 0012. They do not prove runtime code works. Implementation and its real checks remain future work.
        
      
        Unqualified security boundary
        Signer candidate: Secure Enclave with fresh biometric or password confirmation. It remains unqualified. Protected enrollment, authenticated status delivery, same-Mac isolation and real signing are not implemented. Second-machine transfer is simulated.
        
      
        Demo state stays in memory. Reloading loses it. The canonical gallery code stores only theme preference and requests its standard fonts. No workflow data or credentials are stored.
        
      
        The text is STE-inspired. It claims no formal ASD-STE100 compliance.
        
      
        Optional developer checks
        
      
        These controls test the demo’s approval rules by creating sample failures. They can reset sample choices. You do not need them to choose fixes or copy a handoff.
