# The runner briefs each planning phase; prose no longer drives dispatch

Status: accepted

Decision ticket: [Orchestrator weight on the plan stage: digests and plan-only references](https://github.com/racecraft-lab/racecraft-plugins-public/issues/1151), part of [Wayfinder: speckit-pro planning performance](https://github.com/racecraft-lab/racecraft-plugins-public/issues/1144).

On the plan stage, the runner hands the orchestrator a phase brief for the current planning phase: the agent to dispatch, its inputs, the files it may read, and the gate to check afterward. The orchestrator follows the brief instead of re-reading `phase-execution.md` to learn each phase. Executors get only the reference slices their phase needs, placed in their dispatch prompt by the runner, instead of being told to read the four shared references (1,726 lines per spawn).

The measured cost drove this. On the canary fixture, the orchestrator's median context was 171K to 200K tokens across 96 to 132 turns, and about 94% of all plan-stage tokens were cache re-reads. The orchestrator read `phase-execution.md` 6 times, and subagents re-read the same references again and again. A brief is the same on Claude Code and Codex, so it also serves host parity (ADR 0003), and it moves behavior into runner code the tests can see.

## Considered Options

- **Split the prose by stage only.** Rejected as the main fix: the orchestrator would still read prose to learn each phase, so the context cut is limited. A plan-only reference set falls out of the brief anyway.
- **Do the prose split first, then the brief.** Rejected: the split is churn that the brief replaces.
- **Fix only the executors' reads.** Rejected: it leaves the orchestrator's context, the largest token driver, in place.

## Consequences

- The phase 5 prose tickets (#1090 to #1093) stay as total-size cuts. Trimming `phase-execution.md` (#1091) waits on the brief, which makes most of its dispatch prose redundant.
- **Concurrency** ([Parallel dispatch on the plan stage](https://github.com/racecraft-lab/racecraft-plugins-public/issues/1158)): the brief lists waves, meaning the agents to launch in one turn. The analysts of one consensus round form a wave, the analysts for several low-confidence items form a wave, and the checklist domains form a wave. Domains run in check-and-propose mode: each returns its gaps and proposed edits, the runner applies the edits one domain at a time, and the verify re-runs go out as a second wave. Waves are the same on both hosts: background launches in one turn on Claude Code; on Codex, every `spawn_agent` call of the wave in one model response, then a bounded `wait_agent` loop whose calls pass the brief's `wait.codex.timeout_ms`.
- The first Codex plan-stage profile ([profile](../ai/research/2026-10-06-codex-plan-stage-profile.md)) confirmed concurrent dispatch (peak 3 live children, a 2.8 times speed-up over serial) and corrected two details of the line above. The orchestrator issued one `spawn_agent` per model response, not one wave per response: a Codex turn spans many responses (175 in one turn), so "in one turn" did not hold a launch together, and the wording now says one model response. In its second run it also polled `wait_agent` at 10,000 ms on every call, the tool's floor, and 74% of those polls timed out (the first run used 10,000 ms on 20 calls and 50,000 ms on 13, with 55% timing out). The Codex runtime's `wait_agent` returns early on any mailbox update (final-status notices included), so a longer bound adds no latency to a result; the brief carries one bound for the plan stage ([#1286](https://github.com/racecraft-lab/racecraft-plugins-public/issues/1286)). That profile also saw the verify wave go out as `followup_task` calls to the existing checklist threads, not `spawn_agent`. A Codex canary re-run with the one-response wording and the brief's timeout is pending; until it lands, whether the model honors the wording and how many polls the longer bound saves are unconfirmed.
- Upstream Spec Kit's workflow engine was considered for fan-out and rejected. It can coexist with ADR 0010 only as an inner executor, its fan-out would trip the ledger lock (a `concurrent_writer` harm halt), and its engine state would be a second ledger.
- The brief also names the model for each dispatch, because Claude Code's Agent tool takes a per-call model but not a per-call effort; effort stays in the agent file. Codex sets both per spawn. The per-agent table is in [Model and effort per plan-stage agent on each host](https://github.com/racecraft-lab/racecraft-plugins-public/issues/1150).
- **Hooks:** the upstream command runs mandatory extension hooks itself, so the orchestrator no longer dispatches them. The brief lists optional suggestions with their event, optional marker, prompt and description. Prompt and description are fixed runner-owned consent text; contributor display text never enters the confirmation surface. Input file size, display-field length and continuation count are bounded; parser diagnostics omit project field/event names. Only runner-listed optional suggestions are eligible for confirmation; optional Clarify and Implement hooks are skipped because those phases have no runner-listed suggestions. The orchestrator presents the fixed text and validated identifiers and requires explicit operator confirmation for each extension, command and event; otherwise it skips them, including unattended runs. Before hooks stay before dispatch and after hooks stay after completion. Exact duplicates within an event are listed once; a registration in both windows retains separate confirmations. Runs and skips go in the decisions list. This preserves the upstream confirmation boundary while removing double dispatch.
- The brief carries policy facts only. The runner still owns the stop policy (ADR 0010), and the brief never stands in for a gate check.
